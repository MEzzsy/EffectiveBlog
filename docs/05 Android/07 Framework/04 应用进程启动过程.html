04 应用进程启动过程

  • 1. 🌟总结
  • 2. system_server 发送启动请求
  • 3. Zygote 创建应用进程
    • 3.1. fork 与运行环境初始化
    • 3.2. USAP 进程池
  • 4. 主线程初始化与进程注册
  • 5. 创建并初始化 Application
  • 6. 需要记住的版本变化

本文以 AOSP android-17.0.0_r1（Android 17） 为基线，说明普通应用进程的启动过程。

1. 🌟总结

  1. AMS 会先检查目标进程：已有可用进程就复用，否则由 AMS 通过 Socket 请求 Zygote 创建或提供应用进程。
  2. 应用进程完成运行时和 Binder 线程池初始化后，进入 ActivityThread.main()，准备主线程消息循环、向 AMS 注册，再开始分发消息。
  3. AMS 下发 bindApplication 指令，由应用主线程创建 Application 并执行其 onCreate()。

2. system_server 发送启动请求

以 Activity 启动为例，ATMS 负责 Activity 和任务调度，AMS 配合 ProcessList 管理并启动进程。它们都位于 system_server。

普通进程创建的主要调用关系为：

AMS / ProcessList → Process.start() → ZygoteProcess.start()

ProcessList 准备 UID/GID、进程名、ABI、运行时配置等参数，普通应用的入口类是 android.app.ActivityThread。启动序列号 startSeq 用于关联本次请求与后续的进程注册。

ZygoteProcess 根据 ABI 选择对应的 Zygote，通过 LocalSocket（Unix Domain Socket） 发送请求。这段通信不使用 Binder，也不需要 IP 和端口；标准 Zygote Socket 由 init 创建，再交给 Zygote 监听。参见 ProcessList 和 ZygoteProcess。

3. Zygote 创建应用进程

3.1. fork 与运行环境初始化

Zygote 已初始化 ART，并预加载公共框架代码和资源。收到请求后，按需创建路径主要完成：

  1. fork 子进程：继承 ART 的已初始化状态，通过写时复制（Copy-on-Write）等机制共享内存，避免立即完整复制全部物理内存。
  2. 配置子进程：设置 UID/GID、SELinux 上下文、数据挂载等，并清理不需要的文件描述符。
  3. 进入应用入口：子进程完成运行时初始化，启动自己的 Binder 线程池，随后进入 ActivityThread.main()。

父进程 Zygote 返回子进程 PID，并继续等待请求。父子进程并发执行，返回 PID 不代表应用初始化已经完成。

子进程从 fork 返回处继续执行，不会重新从 app_main.cpp 的 main 开始。应用之间的普通 Java 对象和单例也不会因 fork 而共享可变状态。

3.2. USAP 进程池

USAP（Unspecialized App Process）是 Zygote 提前 fork、尚未配置成具体应用的进程。

启用进程池且请求满足条件时，系统将参数交给一个 USAP，由它完成应用专属配置并继续初始化。它将 fork 成本提前，是否使用取决于设备配置和启动策略。参见 AOSP Zygote 说明。

4. 主线程初始化与进程注册

ActivityThread.main() 的核心顺序如下，省略参数解析和环境设置：

Looper.prepareMainLooper();
ActivityThread thread = new ActivityThread();
thread.attach(false, startSeq);
Looper.loop();
  • prepareMainLooper() 准备主线程的 Looper 和 MessageQueue。
  • 创建 ActivityThread 时，会创建 H（Handler）和 ApplicationThread（Binder 接口实现）。
  • attach() 通过 Binder 调用 AMS 的 attachApplication(mAppThread, startSeq)，注册进程并交出系统调用应用所需的接口。
  • Looper.loop() 开始分发消息，无消息可处理时等待。

ActivityThread 是主线程上的框架调度对象，并不继承 Thread；ApplicationThread 也不是一条线程，而是 IApplicationThread.Stub 的实现。 参见 ActivityThread 源码。

5. 创建并初始化 Application

AMS 收到注册请求后，通过 mAppThread.bindApplication() 下发初始化参数。应用侧由 Binder 线程接收，再向 H 发送 BIND_APPLICATION 消息，最终由主线程执行 handleBindApplication()。

Application 在应用进程的主线程中创建和初始化，system_server 负责调度。 常规启动绑定过程的主要顺序是：

handleBindApplication()
  → LoadedApk.makeApplicationInner() 创建 Application
  → Application.attachBaseContext() 绑定 Context
  → 初始化本进程启动时的 ContentProvider，调用其 onCreate()
  → Instrumentation.callApplicationOnCreate()
  → Application.onCreate()

这里的 Provider 顺序限定于普通启动绑定时安装的本进程 Provider。因此，这些 Provider 的 onCreate() 不能默认依赖 Application.onCreate() 已完成。

Application 通常在每个应用进程中分别初始化，不会每启动一个 Activity 就重新创建。应用完成绑定初始化后还会调用 finishAttachApplication()；系统安排后续组件的具体时机受配置影响。

进程创建、Application 初始化和首屏显示是不同阶段。 即使 Application.onCreate() 已返回，也不代表 Activity 已启动或首帧已显示。参见 ActivityThread 和 AMS。

6. 需要记住的版本变化

  • 入口跳转：旧版通过抛出 MethodAndArgsCaller 异常退出初始化调用栈；本文基线返回实现 Runnable 的 MethodAndArgsCaller，逐层返回后执行 run()，反射调用 ActivityThread.main()。参见 RuntimeInit。
  • 消息队列：Android 17 上，面向 API 37 及以上的应用默认使用新的无锁 MessageQueue。Looper、Handler 的基本使用流程保持一致。参见 官方行为变更说明。
