学习目标：了解分布式服务的基本概念、常见通信方式、主要优势及其带来的工程问题。

1. 什么是分布式服务

分布式服务是将一个完整系统拆分为多个相对独立的服务，并把它们部署在不同进程、容器或机器上。各服务通过网络通信，共同完成完整的业务功能。

例如，一个电商系统可以拆分为：

客户端
  ↓
API 网关
  ├── 用户服务
  ├── 商品服务
  ├── 订单服务
  ├── 库存服务
  └── 支付服务

每个服务负责一部分业务能力。例如，订单服务负责创建和查询订单，库存服务负责库存查询与扣减。

2. 为什么使用分布式服务

随着系统规模和团队规模增大，单体应用可能出现代码复杂、发布风险高和扩容成本高等问题。拆分为分布式服务后，可以获得以下能力：

  • 独立开发：不同团队可以负责不同服务。
  • 独立部署：修改订单服务时，不必重新部署整个系统。
  • 独立扩容：流量较大的服务可以单独增加实例。
  • 故障隔离：一个非核心服务故障时，其他服务仍可继续运行。
  • 技术选择灵活：不同服务可以根据需要选择合适的语言和存储方案。

服务拆分并非越细越好。服务数量增加后，网络通信、数据一致性和运维成本也会增加。

3. 服务之间如何通信

3.1. RPC

服务之间像调用本地方法一样发起远程调用：

orderService.createOrder(request)

RPC 适合需要立即获得结果的服务间通信，例如订单服务查询库存。

3.2. HTTP API

服务通过 HTTP 接口进行请求和响应：

GET /inventory/products/1001

HTTP API 通用性强、容易调试，也适合客户端和开放平台访问。

3.3. 消息队列

服务将事件发送到消息队列，由其他服务异步消费：

订单服务 → 订单已创建事件 → 消息队列 → 通知服务

消息队列适合异步处理、流量削峰和事件通知，但消费者需要处理重复消息和消费失败。

4. 一次分布式调用示例

用户提交订单时，可能经历以下过程：

客户端提交订单
→ 网关把请求转发给订单服务
→ 订单服务调用库存服务检查并扣减库存
→ 订单服务调用支付服务创建支付单
→ 订单服务保存订单
→ 发送订单创建事件
→ 通知服务异步发送消息

如果库存扣减成功，但支付服务调用失败，系统就会出现部分成功。因此，分布式服务需要额外设计重试、幂等、补偿和数据一致性机制。

5. 核心基础能力

5.1. 服务注册与发现

服务实例的地址会随着部署、扩容和故障不断变化。服务提供者向注册中心登记地址，调用方从注册中心获取可用实例列表。

5.2. 负载均衡

同一个服务通常部署多个实例。负载均衡会使用随机、轮询或最少活跃等算法选择一个实例，避免流量集中到单台机器。

5.3. 超时与重试

网络请求可能超时或失败，每次远程调用都应该设置超时。只有满足幂等要求并且错误可以恢复时，才能进行有限重试。

5.4. 限流、熔断与降级

  • 限流：控制进入服务的请求量。
  • 熔断：下游持续故障时暂时停止调用。
  • 降级：依赖不可用时返回缓存、默认值或部分结果。

这些机制可以防止单个故障沿调用链扩散到整个系统。

5.5. 可观测性

一次请求可能经过多个服务，因此需要通过日志、指标和分布式追踪定位问题。Trace ID 可以把不同服务产生的调用记录关联起来。

6. 主要挑战

6.1. 网络不可靠

远程调用可能出现连接失败、超时、响应丢失和服务不可用，不能按照本地方法调用的方式处理。

6.2. 数据一致性

不同服务通常拥有独立数据库，无法简单使用单个本地事务保证全部操作同时成功。常见方案包括可靠事件、补偿事务、Saga 和后台对账。

6.3. 调用链故障

服务之间的调用链越长，整体延迟和失败概率越高。需要控制调用深度，并设置超时预算、熔断和隔离。

6.4. 运维复杂度

服务数量增加后，需要管理部署、配置、监控、日志、版本兼容、容量和安全权限，通常需要容器平台和自动化运维系统提供支持。

7. 分布式服务与微服务

分布式服务强调多个进程或机器通过网络协作。微服务是在分布式系统基础上进一步强调服务小型化、业务边界和独立交付。

因此：

微服务通常是分布式服务
分布式服务不一定采用微服务架构

7.1. 采用微服务的好处

  • 业务边界清晰：按照用户、订单、库存等业务能力拆分，降低单个服务的代码复杂度。
  • 独立开发和部署：不同团队可以分别迭代服务，修改一个服务不必发布整个系统。
  • 独立扩容：只扩容流量较大的服务，减少不必要的资源消耗。
  • 故障隔离：非核心服务故障时，可以通过熔断和降级避免整个系统不可用。
  • 技术选择灵活：不同服务可以根据业务特点选择合适的语言、框架和存储方案。

7.2. 采用微服务的坏处

  • 分布式通信复杂：本地调用变成网络调用，需要处理超时、重试、幂等和服务不可用。
  • 数据一致性困难：跨服务操作无法简单依赖单个数据库事务，需要可靠事件、补偿或对账机制。
  • 运维成本增加：需要管理大量服务的部署、配置、监控、日志、容量和安全权限。
  • 排查与测试困难：一次请求可能经过多个服务，需要分布式追踪和完整的集成测试环境。
  • 接口治理复杂：服务独立发布后，需要处理接口兼容、版本升级和调用方依赖关系。
  • 拆分过细会降低性能：服务之间产生大量网络调用，调用链变长，延迟和故障概率随之增加。

微服务更适合业务规模较大、模块边界清晰且团队具备自动化部署和服务治理能力的系统。对于规模较小或业务仍在快速变化的项目，结构清晰的单体应用通常成本更低。

8. 总结

分布式服务通过拆分和独立部署提高系统的扩展能力与团队协作效率，但也把本地调用变成了不可靠的网络调用，并引入数据一致性、服务治理和运维复杂度。

使用分布式架构前，应确认系统规模和业务需求确实需要拆分，避免为了架构形式过早增加复杂度。
