# 渠道包是什么

渠道包是**带有分发来源标识的 Android 安装包**，例如官网包、小米渠道包、华为渠道包。应用读取包内渠道号并上报，用来统计各渠道的激活、注册、留存和付费。

不同渠道包可以使用相同的代码、资源、包名和签名，只在渠道号上不同；也可以包含各渠道专属的登录、支付或推送 SDK。

**只修改 APK 文件名不能让应用识别渠道**，渠道信息需要写入包内，并由应用主动读取。

# 两种常见实现方式

| 方式 | 做法 | 适用场景 |
| --- | --- | --- |
| Gradle `productFlavors` | 构建时生成不同变体，将渠道写入 Manifest 等配置 | 渠道较少，或代码、资源、SDK 存在差异 |
| Walle 等渠道工具 | 构建一个已签名的母包，再批量写入渠道元数据 | 渠道很多，业务内容相同，仅渠道号不同 |

## Gradle 多渠道构建

在应用模块的 `build.gradle.kts` 中配置，以下省略项目已有的 SDK 和签名配置：

```kotlin
android {
    flavorDimensions += "distribution"
    productFlavors {
        listOf("official", "xiaomi", "huawei").forEach { channel ->
            create(channel) {
                dimension = "distribution"
                manifestPlaceholders["APP_CHANNEL"] = channel
            }
        }
    }
}
```

在 Manifest 的 `<application>` 内声明：

```xml
<meta-data
    android:name="APP_CHANNEL"
    android:value="${APP_CHANNEL}" />
```

执行 `./gradlew :app:assembleXiaomiRelease` 后，构建系统将占位符替换为 `xiaomi`。应用再通过 `PackageManager` 携带 `GET_META_DATA` 查询自身的 `ApplicationInfo`，从 `metaData` 中读取 `APP_CHANNEL`。

若渠道有功能差异，可以把专属内容放在 `src/xiaomi/` 等源集中，并用 `xiaomiImplementation` 配置专属依赖。渠道越多，构建和验证成本通常越高，但 Gradle 仍可复用部分任务与缓存。[Android 构建变体](https://developer.android.com/build/build-variants)、[Manifest 占位符](https://developer.android.com/build/manage-manifests#inject_build_variables_into_the_manifest)

## 一次构建，批量写入渠道号

如果各渠道只差一个字符串，可以先生成一个母包，再派生多个渠道包：

```text
已签名的母包 APK
    ├── 写入 official → 官网包
    ├── 写入 xiaomi   → 小米渠道包
    └── 写入 huawei   → 华为渠道包
```

以 Walle 为例，母包需要提前集成渠道读取库，并包含工具要求的 v2 签名。命令行可以批量生成：

```bash
java -jar walle-cli-all.jar batch -c official,xiaomi,huawei app-release.apk
```

运行时通过 `WalleChannelReader.getChannel(context)` 读取渠道号。这个过程不需要为每个渠道重新编译业务代码，但仍有文件复制和读写成本。[Walle 项目与使用说明](https://github.com/Meituan-Dianping/walle)

# Walle 为什么不破坏签名

带有 v2 签名的 APK 可以简化为：

```text
ZIP 文件内容：Manifest、DEX、资源等
APK Signing Block
    ├── v2 / v3 等签名条目
    └── 自定义渠道条目
ZIP Central Directory
ZIP End of Central Directory（EOCD）
```

**Signing Block 是容器，签名条目和渠道条目是其中不同的内容。** Walle 添加自定义的 ID-value 条目，并修正块长度和相关偏移。

v2 校验保护 ZIP 内容、中央目录、EOCD 和签名块内的 `signed data`，但不保护普通自定义渠道条目。计算 EOCD 摘要时，中央目录偏移还会按规范替换为 Signing Block 起始偏移，因此正确扩展容器不会改变原有摘要结果。[AOSP v2 签名规范](https://source.android.com/docs/security/features/apksigning/v2)

由此可以理解两个常见问题：

- **为什么旧方案不能直接用？** 签名后修改 ZIP Comment 或向 `META-INF` 添加渠道文件，会改变 v2 保护的数据或破坏签名结构。
- **渠道号能防篡改吗？** 普通渠道条目不受上述签名保护，不能单独作为分成或权益发放的可信凭证。

# 实际使用时注意什么

- **处理顺序**：通常先构建、加固（如需要）、对齐、正式签名，再写渠道，最后校验。重签名可能清除渠道信息；需要 v4 时，应针对最终 APK 生成匹配的 `.idsig`。[apksigner 说明](https://developer.android.com/tools/apksigner)
- **校验最终产物**：使用 `apksigner verify --verbose --print-certs app.apk` 检查签名，同时确认渠道读取正确，并验证安装和升级。旧版工具是否兼容当前签名组合，需要实际验证。
- **覆盖安装**：主要取决于相同的包名、兼容的签名身份和版本规则，渠道字符串本身不影响应用身份。不要仅为统计渠道就修改 `applicationId`。
- **统计口径**：包内渠道跟随 APK，转发不会改变它；升级可能换成其他渠道包，因此当前包渠道与首次获客渠道应分开记录。
- **Google Play / AAB**：AAB 由 Play 生成并签名最终 APK，不能直接套用 Walle。推广活动通常通过 Install Referrer 等机制区分，无需每次都生成新渠道包。[AAB 说明](https://developer.android.com/guide/app-bundle)、[Install Referrer](https://developer.android.com/google/play/installreferrer)
