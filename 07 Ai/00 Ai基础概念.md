# 模型基础

## 大语言模型

大语言模型（LLM）是在大量文本上训练的深度学习模型，能够理解并生成人类语言。

# 输入与输出

## Token

Token 是模型处理文本时使用的基本单位，可以是一个字、一个词或词的一部分。

## 上下文窗口

上下文窗口是模型一次能够读取和处理的 Token 数量上限，包含输入内容和生成内容。

## 提示词

提示词（Prompt）是用户提供给模型的指令、问题和背景信息，用于引导模型生成符合预期的结果。

# 知识增强

## Embedding

Embedding（嵌入）是将文本、图片等内容转换为数值向量，以便计算机比较它们的语义相似度。

## 向量数据库

向量数据库用于存储和检索向量，能够快速找出与查询内容在语义上相近的数据。

## RAG

RAG（检索增强生成）是先从外部知识库检索相关信息，再让模型结合这些信息生成答案的技术。

# 智能体

## Agent

Agent（智能体）是一个能够围绕目标自主完成任务的 AI 执行者。可以简单理解：

```
Agent ≈ 身份与行为规则 + 模型 + Agent Runtime
```

- 身份与行为规则：规定职责、工作方式和约束，例如“担任代码审查员，重点检查正确性，只提出建议”。
- 模型：理解 + 决策。
- Agent Runtime：组织上下文、调用模型、调度工具、管理状态，驱动 Agent Loop 持续运行。

## Harness

### Harness 是什么？

在 AI Agent 语境中，Harness 是围绕模型搭建的一套执行与控制系统，让模型能够使用工具、获得反馈，并持续完成任务。

它通常包含：

- **上下文管理**：组织任务、规则、历史消息和工具结果。
- **执行循环**：调用模型，处理模型输出，再决定是否继续。
- **工具调度**：把模型提出的操作请求交给工具执行。
- **状态管理**：维护进度，支持中断和恢复。
- **权限控制**：落实操作范围、沙箱限制和审批策略。

比如模型提出“运行测试”，Harness 负责安排执行、接收日志，并把结果交回模型。这些机制让模型能够根据真实结果继续工作。

### Harness 和 Agent Runtime区别

> - Agent Runtime：强调 Agent 如何运行，如启动任务、执行工具、维护状态。
> - Harness：强调模型周围如何配套和约束，如组织上下文、提供工具、设置权限与反馈循环。
>
> 在 Codex 中，两者高度重叠，主要是观察角度不同。

以 Codex 为例，两者大量重叠，不能据此划分出两个独立组件。

| 名称          | 强调的角度                           | Codex 中的体现                               |
| ------------- | ------------------------------------ | -------------------------------------------- |
| Harness       | 模型周围有哪些机制，让它能够完成任务 | 上下文组织、工具接入、反馈循环、权限策略     |
| Agent Runtime | 哪套软件负责驱动和管理 Agent 的运行  | 调用模型、执行工具、维护会话、启动与中断任务 |

因此，可以把 Codex Harness 理解为一套具体的 Agent Runtime 实现。 这是帮助理解的说法，并非统一的术语分类。OpenAI 的介绍也同时使用 Harness 和 Runtime 来描述这套可复用的执行系统。[Codex 官方介绍](https://developers.openai.com/blog/codex-as-a-platform)

例如，`codex app-server` 提供创建会话、开始任务、接收执行事件等接口。从应用开发者角度，你在使用 Agent Runtime；从模型如何获得上下文、调用工具和持续工作的角度，你在使用 Codex Harness。[App Server 文档](https://learn.chatgpt.com/docs/app-server)

**例子一：在 CI 中尝试修复失败测试**

可以设计这样的流程：CI 测试失败后，通过适合非交互任务的 `codex exec`，把仓库、失败日志和修复要求交给 Codex。[CLI 文档](https://learn.chatgpt.com/docs/cli/reference)

```
CI 提供失败日志
    ↓
Codex 读取相关代码
    ↓
模型分析问题，提出修改
    ↓
工具应用修改、运行测试
    ↓
结果交回模型，继续修正或结束
    ↓
CI 独立验收修改
```

这里，模型负责分析和提出行动；**Codex Harness 支撑读取、修改、测试、反馈这一整套循环**。CI 负责触发任务和最终验收。你复用了现成的 Agent Runtime，无须自己重新实现模型与工具的交互循环。

**例子二：把 Codex 嵌入物流业务系统**

OpenAI 的 **Relay 演示应用**使用 `codex app-server`，在物流看板旁放置一个智能体，并接入应用提供的 MCP 工具。用户选择异常货运记录后，智能体读取相关数据、比较处理方案；涉及重新订舱等操作时，示例要求人工批准。它使用的是虚构示例数据。[Relay 官方案例](https://developers.openai.com/blog/codex-as-a-platform#example-relay)

这个应用中的分工是：

| 部分          | 负责什么                                                   |
| ------------- | ---------------------------------------------------------- |
| 物流应用      | 页面、业务数据、业务规则及操作接口                         |
| 模型          | 分析异常，比较方案，提出下一步行动                         |
| Codex Harness | 维护上下文与会话、调度工具、推进循环、处理配置好的审批流程 |

同一套 Codex Harness，接入代码工具可以支持修复程序，接入物流工具也可以支持业务处理。更换的是任务、规则和工具，底层驱动 Agent 工作的机制可以继续复用。

# 能力扩展

## Skill

Skill（技能）是一套可复用的任务说明和操作流程，用来告诉 AI 某类任务应该怎么做。通常以 `SKILL.md` 描述，也可以附带脚本、模板和参考资料。

例如，“代码审查 Skill”可以规定：先理解改动，再检查潜在问题，最后按统一格式输出审查结果。

## MCP

MCP（Model Context Protocol，模型上下文协议）是一种让 AI 应用连接外部工具和数据源的标准协议。实现该协议的 MCP 服务可以提供查询数据、读取文件等能力，由 AI 应用发现并调用。

例如，GitHub MCP 服务可以提供读取 PR 和代码的工具，让 AI 获取审查所需的内容。MCP 规定连接与交互方式，具体功能由服务实现。

## Plugin

Plugin（插件）是给应用增加功能的可安装扩展包。在 Codex 等 AI 应用中，一个插件可以把 Skill、MCP 服务配置及相关资源打包在一起，方便安装和使用；具体包含哪些内容取决于平台和插件本身。[参考：Plugin 文档](https://developers.openai.com/plugins/build/plugins)

例如，“代码审查插件”可以同时提供代码审查 Skill 和 GitHub MCP 服务的连接配置。

## 三者的区别

| 概念 | 主要作用 | 通俗理解 |
| --- | --- | --- |
| Skill | 定义任务的做法和流程 | 操作手册 |
| MCP | 统一 AI 应用与外部工具、数据的交互方式 | 接口标准 |
| Plugin | 打包和分发扩展能力 | 扩展安装包 |

三者可以配合使用，也可以独立使用：Skill 不一定需要 MCP，Plugin 也不一定同时包含 Skill 和 MCP 配置。
