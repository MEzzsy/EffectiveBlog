# 模型基础

## 大语言模型

大语言模型（LLM）是在大量文本上训练的深度学习模型，能够理解并生成人类语言。

# 输入与输出

## Token

Token 是模型处理文本时使用的基本单位，可以是一个字、一个词或词的一部分。

## 上下文窗口

上下文窗口是模型一次能够读取和处理的 Token 数量上限，包含输入内容和生成内容。

## 提示词

提示词（Prompt）是用户提供给模型的指令、问题和背景信息，用于引导模型生成符合预期的结果。

# 智能体

## Agent

Agent（智能体）是一个能够围绕目标自主完成任务的 AI 执行者。可以简单理解：

```
Agent ≈ 身份与行为规则 + 模型 + Agent Runtime
```

- 身份与行为规则：规定职责、工作方式和约束，例如“担任代码审查员，重点检查正确性，只提出建议”。
- 模型：理解 + 决策。
- Agent Runtime：组织上下文、调用模型、调度工具、管理状态，驱动 Agent Loop 持续运行。

## Harness

### Harness 是什么？

在 AI Agent 语境中，Harness 是围绕模型搭建的一套执行与控制系统，让模型能够使用工具、获得反馈，并持续完成任务。

它通常包含：

- **上下文管理**：组织任务、规则、历史消息和工具结果。
- **执行循环**：调用模型，处理模型输出，再决定是否继续。
- **工具调度**：把模型提出的操作请求交给工具执行。
- **状态管理**：维护进度，支持中断和恢复。
- **权限控制**：落实操作范围、沙箱限制和审批策略。

比如模型提出“运行测试”，Harness 负责安排执行、接收日志，并把结果交回模型。这些机制让模型能够根据真实结果继续工作。

### Harness 和 Agent Runtime区别

> - Agent Runtime：强调 Agent 如何运行，如启动任务、执行工具、维护状态。
> - Harness：强调模型周围如何配套和约束，如组织上下文、提供工具、设置权限与反馈循环。
>
> 在 Codex 中，两者高度重叠，主要是观察角度不同。

以 Codex 为例，两者大量重叠，不能据此划分出两个独立组件。

| 名称          | 强调的角度                           | Codex 中的体现                               |
| ------------- | ------------------------------------ | -------------------------------------------- |
| Harness       | 模型周围有哪些机制，让它能够完成任务 | 上下文组织、工具接入、反馈循环、权限策略     |
| Agent Runtime | 哪套软件负责驱动和管理 Agent 的运行  | 调用模型、执行工具、维护会话、启动与中断任务 |

因此，可以把 Codex Harness 理解为一套具体的 Agent Runtime 实现。 这是帮助理解的说法，并非统一的术语分类。OpenAI 的介绍也同时使用 Harness 和 Runtime 来描述这套可复用的执行系统。[Codex 官方介绍](https://developers.openai.com/blog/codex-as-a-platform)

例如，`codex app-server` 提供创建会话、开始任务、接收执行事件等接口。从应用开发者角度，你在使用 Agent Runtime；从模型如何获得上下文、调用工具和持续工作的角度，你在使用 Codex Harness。[App Server 文档](https://learn.chatgpt.com/docs/app-server)

**例子一：在 CI 中尝试修复失败测试**

可以设计这样的流程：CI 测试失败后，通过适合非交互任务的 `codex exec`，把仓库、失败日志和修复要求交给 Codex。[CLI 文档](https://learn.chatgpt.com/docs/cli/reference)

```
CI 提供失败日志
    ↓
Codex 读取相关代码
    ↓
模型分析问题，提出修改
    ↓
工具应用修改、运行测试
    ↓
结果交回模型，继续修正或结束
    ↓
CI 独立验收修改
```

这里，模型负责分析和提出行动；**Codex Harness 支撑读取、修改、测试、反馈这一整套循环**。CI 负责触发任务和最终验收。你复用了现成的 Agent Runtime，无须自己重新实现模型与工具的交互循环。

**例子二：把 Codex 嵌入物流业务系统**

OpenAI 的 **Relay 演示应用**使用 `codex app-server`，在物流看板旁放置一个智能体，并接入应用提供的 MCP 工具。用户选择异常货运记录后，智能体读取相关数据、比较处理方案；涉及重新订舱等操作时，示例要求人工批准。它使用的是虚构示例数据。[Relay 官方案例](https://developers.openai.com/blog/codex-as-a-platform#example-relay)

这个应用中的分工是：

| 部分          | 负责什么                                                   |
| ------------- | ---------------------------------------------------------- |
| 物流应用      | 页面、业务数据、业务规则及操作接口                         |
| 模型          | 分析异常，比较方案，提出下一步行动                         |
| Codex Harness | 维护上下文与会话、调度工具、推进循环、处理配置好的审批流程 |

同一套 Codex Harness，接入代码工具可以支持修复程序，接入物流工具也可以支持业务处理。更换的是任务、规则和工具，底层驱动 Agent 工作的机制可以继续复用。

# 能力扩展

## Skill

Skill（技能）是一套可复用的任务说明和操作流程，用来告诉 AI 某类任务应该怎么做。通常以 `SKILL.md` 描述，也可以附带脚本、模板和参考资料。

例如，“代码审查 Skill”可以规定：先理解改动，再检查潜在问题，最后按统一格式输出审查结果。

### skill多了之后如何快速查找

skill 多了以后，需要分别解决人怎么找和模型怎么选：

1. 可以直接指定

2. 你只知道需求：先让它筛选候选。
   可以直接说：“从当前可用技能中，找出最适合检查 PDF 排版的 3 个，说明区别，先不要执行。”这样更容易看出是否选错。

3. 让名称和描述有区分度。
   名称宜具体，例如 `pdf-layout-review`；描述写清“处理什么、什么时候用、哪些相似场景不适用”。例如：

   ```
   name: pdf-layout-review
   description: 检查 PDF 的分页、字体、图表裁切和版面溢出；用于交付前视觉验收，不用于仅提取文本。
   ```

   核心用途尽量放前面，因为描述可能被截短。

4. 控制每个项目的候选范围。
   项目专用技能放项目目录，通用技能放用户目录；停用重复、过时的技能。按领域命名有助于区分，但不能假设目录分组会自动成为模型的分层检索机制。

5. 规模很大时，引入真正的检索层。
   如果你在设计自己的技能平台，可以使用：

   ```
   用户需求 → 按项目/领域过滤 → 关键词或语义检索 → 少量候选 → 读取完整技能
   ```

   这是扩展架构建议，不能直接当作 Codex 默认内部实现。

还有一个直接影响“大量 skill”的限制：当前官方文档说明，初始技能目录默认最多占模型上下文的 2%；数量过多时会先缩短描述，必要时省略部分技能并提示。 可以通过 `skills.max_context_tokens` 调整预算，但增加预算也会增加上下文占用。[技能目录预算](https://learn.chatgpt.com/docs/build-skills)

因此，快速定位最有效的组合是：明确调用名、写好描述、缩小当前项目的候选集合；规模再大时，用检索返回少量候选。

## MCP

MCP（Model Context Protocol，模型上下文协议）是一种让 AI 应用连接外部工具和数据源的标准协议。实现该协议的 MCP 服务可以提供查询数据、读取文件等能力，由 AI 应用发现并调用。

例如，GitHub MCP 服务可以提供读取 PR 和代码的工具，让 AI 获取审查所需的内容。MCP 规定连接与交互方式，具体功能由服务实现。

## Plugin

Plugin（插件）是给应用增加功能的可安装扩展包。在 Codex 等 AI 应用中，一个插件可以把 Skill、MCP 服务配置及相关资源打包在一起，方便安装和使用；具体包含哪些内容取决于平台和插件本身。[参考：Plugin 文档](https://developers.openai.com/plugins/build/plugins)

例如，“代码审查插件”可以同时提供代码审查 Skill 和 GitHub MCP 服务的连接配置。

## 三者的区别

| 概念 | 主要作用 | 通俗理解 |
| --- | --- | --- |
| Skill | 定义任务的做法和流程 | 操作手册 |
| MCP | 统一 AI 应用与外部工具、数据的交互方式 | 接口标准 |
| Plugin | 打包和分发扩展能力 | 扩展安装包 |

三者可以配合使用，也可以独立使用：Skill 不一定需要 MCP，Plugin 也不一定同时包含 Skill 和 MCP 配置。

## Function Calling / Tool Calling、Tool、MCP区别

**MCP 是通信协议，实际执行由应用程序和工具服务完成。** 可以调整为：

- **Function Calling / Tool Calling**：让模型根据工具定义，生成“调用哪个工具、传什么参数”的结构化请求。
- **Tool**：提供具体能力，例如读取文件、执行编译。
- **MCP**：规范应用与工具服务之间如何发现工具、发起调用、返回结果。

典型链路是：

**模型生成调用请求 → 应用通过 MCP 调用工具服务 → 工具执行 → 结果回传给模型。**

应用也可以直接执行本地工具，不必经过 MCP。

## 三者如何被发现的

以 Codex 为例，“发现”分两步：宿主程序先找到并登记能力，模型再根据当前任务选择使用。 Skill、Tool、MCP 处在不同层：

| 概念      | 是什么                                          | 如何被发现                                               |
| --------- | ----------------------------------------------- | -------------------------------------------------------- |
| **Skill** | 工作流说明，通常是 `SKILL.md`，可附带脚本、模板 | Codex 从技能目录、已安装插件等来源读取元数据，供模型选择 |
| **Tool**  | 可执行接口，如读文件、搜索、查询 GitHub         | 宿主提供工具目录与参数定义，模型选择并生成调用参数       |
| **MCP**   | 连接外部工具和上下文的协议                      | 宿主按配置连接 MCP Server，再取得它提供的能力            |

因此，一个 skill 可以指导模型组合多个 tool；其中部分 tool 可能由 MCP Server 提供。Skill 本身不一定需要 MCP，Tool 也不一定来自 MCP。

### 发现Skill

Skill 的发现过程可以表示为：

```
技能目录 / 插件
    ↓
读取 name、description、文件路径
    ↓
模型根据任务选择，或用户明确指定
    ↓
读取完整 SKILL.md
    ↓
按需读取参考资料、运行脚本、调用工具
```

这叫“渐进式加载”：先看目录，选中后再看正文。

自动选择主要依赖 `description` 是否与任务匹配。所以，只把适用场景写在正文深处，对初次发现帮助有限；关键用途和边界应放在描述中。

### 发现Tool和MCP

Tool 和 MCP 的发现过程则是：

```
内置工具注册 ───────────────────┐
                              ↓
MCP 配置 → 连接 Server → 可用工具目录 → 模型选择 → 宿主执行
```

Codex 可以从配置文件或插件配置取得 MCP Server 信息，启动本地服务或连接远程服务，再建立工具目录。工具定义通常包含名称、描述和参数 schema。模型负责选择、填写参数，实际调用由宿主执行。

工具定义也可以延迟加载，因此不能把它理解成“所有工具的完整说明永远都塞在上下文里”；具体策略取决于客户端和版本。

比如这次回答，我先从可用技能目录选到 `openai-docs`，读取它的说明，再查找并调用文档搜索、读取工具。这就是一次实际的“目录 → 技能 → 工具”过程。

# vibe coding和spec coding

个人理解：vibe coding的工作方式是描述想法，让 AI 生成，运行后继续调整。需求在对话中补充，但是当对话上下文变多，可能会遗漏一些条件，导致修改可能逐渐失控。spec coding就是将需求、约束、验证内容持久保存在文件中，防止AI跑偏。

| 维度     | Vibe Coding                          | Spec Coding（通常称为规格驱动开发，SDD） |
| -------- | ------------------------------------ | ---------------------------------------- |
| 工作方式 | 描述想法，让 AI 生成，运行后继续调整 | 先明确规格，再据此规划、实现和验证       |
| 需求表达 | 主要在对话中逐步补充                 | 将功能、约束、验收条件写清楚             |
| 调整依据 | “运行效果怎样，哪里需要改”           | “实现是否满足规格，规格是否需要更新”     |
| 优势     | 启动快，方便探索想法                 | 边界清晰，方便协作和核查                 |
| 代价     | 容易遗漏边界，修改可能逐渐失控       | 需要编写、审阅和维护规格                 |

**两者都可以迭代，区别在于需求和验收条件是否被明确下来，并持续指导实现。**

## spec 具体包含什么，为什么需要这一步？

spec主要包含边界和约束、具体做什么、验证内容。

spec的作用：

1. 精简内容，减少上下文占用。spec 提炼需求、技术方案和用例中的关键信息，减少重复查询和上下文占用。
2. 首先，需求、技术方案和用例通常分散描述目标、实现方式和预期结果。整理成 spec 能够集中在同一份文件中。

我们先把技术方案整理成 spec，目的是给后续编码建立明确的实现依据。它会说明本次功能范围、页面交互、技术约束，以及对应的验收条件。这样 Agent 生成代码和修复问题时，都能围绕同一份约定执行，也方便最后核对有没有遗漏需求。
