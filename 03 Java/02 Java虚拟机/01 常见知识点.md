# volatile

## 指令重排序优化

**指令重排序优化**是指：编译器或 CPU 为了提高执行效率，在不改变单线程可观察结果的前提下，调整指令或内存访问的顺序。

例如，下面两条语句没有依赖关系：

```
int a = 1;
int b = 2;
```

先给 `b` 赋值，再给 `a` 赋值，结果仍然相同，因此存在调整顺序的空间。

但在**多线程共享数据**时，另一个线程可能观察到这种顺序变化：

```java
// 共享字段，初始 data = 0、ready = false
int data = 0;
boolean ready = false;

// 线程 A
data = 42;
ready = true;

// 线程 B
if (ready) {
    System.out.println(data);
}
```

线程 A 本来想表达“先准备数据，再通知”。

但没有同步约束时，线程 B **可能先观察到 `ready = true`，却还没观察到 `data = 42`**，于是打印 `0`。这可能来自编译器重排，也可能来自硬件访存的可见顺序。

## volatile特性

>   原子性是指一个操作是不可中断的，要么全部执行成功要么全部执行失败。即使在多个线程一起执行的时候，一个操作一旦开始，就不会被其他线程所干扰。

当一个变量定义为volatile，它将具备两种特性：

1. **可见性**
   保证此变量对所有线程的可见性，指当一条线程修改了这个变量的值，新值对于其他线程来说是可以立即得知的（其他线程持有的变量旧副本会被失效，后续读取时要通过缓存系统取得有效的数据）
   由于volatile变量只能保证可见性，不能保证原子性。在不符合以下两条规则的运算场景下，仍然要通过加锁的方式来保证原子性：

   - 运算结果并不依赖变量的当前值（像这种情况就不能：i++），或者能够确保只有单一的线程修改变量的值。
   - 变量不需要与其他的状态变量共同参与不变约束。

   简单地说就是，volatile只保证只读只写的情况，对于同时读写的情况不能保证。

   volatile修饰的变量如果是对象或数组之类的，其含义是对象或数组的地址具有可见性，但是数组或对象内部的成员改变不具备可见性。

2. **禁止指令重排序优化**

   有volatile修饰后，变量赋值会多执行一个内存屏障操作（重排序时不能把后面的指令重排序到内存屏障之前的位置，换句话说，执行这条指令时，前面的指令已经执行完了）。

## volatile原理

在部分虚拟机实现上，volatile变量在赋值后会多一个指令`lock addl$0x0，(%esp)`，这个指令相当于内存屏障，这个内存屏障保证在指令重排序时不能把后面的指令重排序到内存屏障之前的位置，就是禁止指令重排序优化。

另外，lock前缀的作用是将本处理器的缓存写入了内存，该写入动作也会引起别的处理器或者别的内核的缓存无效化，通过这样一个空操作，可让前面volatile变量的修改对其他处理器立即可见。

## DCL失效问题

**DCL（Double-Checked Locking，双重检查锁）失效的核心问题是：其他线程可能拿到非空的对象引用，却看不到对象正确初始化后的字段值。**

先看没有使用 `volatile` 的代码：

```
class Singleton {
    private static Singleton instance; // 问题在这里

    private int value;

    private Singleton() {
        value = 42;
    }

    static Singleton getInstance() {
        if (instance == null) {              // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null) {      // 第二次检查
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }

    int getValue() {
        return value;
    }
}
```

两次检查分别有不同目的：

- **第一次检查**：对象已经创建时，直接返回，省去获取锁的开销。
- **第二次检查**：等待锁的过程中，其他线程可能已经创建了对象，拿到锁后必须重新确认。

问题出在这一句：

```
instance = new Singleton();
```

它涉及对象空间分配、字段初始化和共享引用赋值。可以抽象成：

```
分配对象空间
    ↓
初始化字段：value = 42
    ↓
发布引用：instance 指向这个对象
```

这和前面的例子有直接对应关系：

```
data = 42;     // 准备数据
ready = true;  // 发布标志
```

在 DCL 中，**`instance != null` 承担了“对象准备好了”的标志作用**。

但 `instance` 是普通字段，缺少安全发布保证。另一个线程可能先观察到引用非空，却还没有观察到构造方法对 `value` 的写入：

```
线程 B 看到 instance != null
             ↓
跳过 synchronized
             ↓
取得对象，调用 getValue()
             ↓
可能读到默认值 0，而不是 42
```

这常被简化为“引用赋值和初始化发生了重排序”。更准确地说，是**引用的可见性与初始化写入的可见性之间，缺少所需的顺序保证**；不要求每次都真的把整个构造方法挪到引用赋值之后。[安全发布分析](https://shipilev.net/blog/2014/safe-public-construction/)

**已经用了 `synchronized`，为什么还不够？**

因为锁的可见性保证，需要读写双方通过**同一把锁**建立联系：

```
线程 A 释放锁 → 线程 B 随后获取同一把锁
```

而 DCL 的快速路径正好绕开了这个过程：

```
if (instance == null) {
    // 只有为 null 才进入同步块
}

return instance; // 非空时，完全没有获取锁
```

创建线程持有锁，并不能自动保护这些没有获取锁的读取。

修复方式是把共享引用声明为 `volatile`：

```
private static volatile Singleton instance;
```

这样就建立了：

```
构造方法写 value = 42
           ↓
volatile 写 instance：发布对象
           ↓
volatile 读 instance：获取对象
           ↓
读取 value，得到 42
```

在 Java 5 及之后的内存模型中，正确使用 volatile 可以修复这种 DCL 发布问题。[JSR-133 FAQ](https://www.cs.umd.edu/~pugh/java/memoryModel/jsr-133-faq.html#dcl)

这里，`synchronized` 负责让创建过程互斥执行，锁内第二次检查避免重复创建；`volatile` 负责让跳过锁的读取路径也能安全地获取初始化结果。

# synchronized

`synchronized` 是 Java 中的关键字。作用是用于互斥同步，通过对象锁，保证同一时刻只有一个线程执行同步代码。

## 加锁实现

Java 中每个对象都关联一个监视器（Monitor）。线程进入同步区域前获取对象锁，退出时释放锁，包括因为异常而退出。

- **锁谁**：实例同步方法锁 `this`；静态同步方法锁对应的 `Class` 对象；同步代码块锁括号里的对象。
- **可重入**：线程已经持有某个锁时，可以再次获取它；每次获取都需要对应一次释放。



字节码层面：

- 同步代码块使用 `monitorenter` / `monitorexit`
- 同步方法通过 `ACC_SYNCHRONIZED` 标志让 JVM 管理加锁和释放

它们最终都操作对象的 Monitor（监视器）。可以先把 Monitor 理解为记录着“谁持有锁、重入了几次”的机制。

**`monitorenter`：尝试获取锁。**

它从操作数栈取出锁对象的引用，然后：

- 没有线程持有锁：当前线程获得锁，计数设为 `1`。
- 当前线程已经持有锁：计数加 `1`，这就是可重入。
- 其他线程持有锁：当前线程需要等待，直到能够获得锁，才能继续执行后面的代码。

**`monitorexit`：释放一次锁。**

只有持有锁的线程才能执行释放，计数减 `1`：

- 计数仍大于 `0`：当前线程继续持有锁。
- 计数变成 `0`：真正释放锁，其他线程可以竞争。

所以，同一个线程加锁两次，就需要释放两次。编译器还会生成异常处理路径，确保同步代码块因为异常退出时，也会执行 `monitorexit`。

**`ACC_SYNCHRONIZED`：告诉 JVM“这个方法执行前必须获取锁”。**

它是方法上的一个标志位。JVM 调用方法时识别这个标志，自动完成：

```
确定锁对象 → 获取锁 → 执行方法体 → 正常返回或异常退出时释放锁
```

这些是 JVM 必须保证的行为规则；实际执行时，JVM 可以通过轻量级锁、自旋等方式减少开销。



## 锁优化

**为什么要锁优化**

加锁和解锁本身存在开销。锁竞争还可能导致线程阻塞与唤醒，而线程的阻塞和唤醒需要耗费很多的处理器时间。所以synchronized是Java语言中一个重量级的操作。



锁优化就是：**在保证线程安全的前提下，让没有竞争时的加锁更便宜，减少不必要的加锁和线程阻塞。**

主要有两类思路：

| 优化                  | 简单理解                                                     |
| --------------------- | ------------------------------------------------------------ |
| **轻量级加锁**        | 无竞争时，通过 CAS 等原子操作快速完成加锁，减少进入复杂监视器路径的开销 |
| **自旋 / 自适应自旋** | 暂时拿不到锁，先忙等一小会儿；如果锁很快释放，就省掉阻塞和唤醒的成本。自适应表示等待策略会根据运行情况调整 |
| **锁消除**            | JIT 证明某个对象不会被其他线程访问，就可能去掉其不必要的加锁 |
| **锁粗化**            | 连续多次对同一个对象加锁，JIT 可能合并成一次，减少反复加锁和解锁 |



### 锁粗化

把连续的小同步区域合并成一个大同步区域。

原本是：

```
加锁 → 操作 A → 解锁
加锁 → 操作 B → 解锁
加锁 → 操作 C → 解锁
```

优化后：

```
加锁 → 操作 A → 操作 B → 操作 C → 解锁
```

这样，加锁和解锁从 3 次减少到 1 次，节省了重复操作的开销。前提是使用同一把锁，并且 JIT 判断合并不会破坏程序的正确性。

## 锁池和等待池

在java中，每个对象都有两个池，monitor（简单理解为锁池）和等待池。

-   锁池：假设线程A已经拥有了某个对象的锁，而其它的线程想要调用这个对象的某个synchronized方法(或者synchronized块)，由于这些线程在进入对象的synchronized方法之前必须先获得该对象的锁的拥有权，但是该对象的锁目前正被线程A拥有，所以这些线程就进入了该对象的锁池中。
-   等待池：假设一个线程A调用了某个对象的wait()方法，线程A就会释放该对象的锁后，进入到了该对象的等待池中



问题：为什么wait或者notify需要拿到锁？

首先没拿到锁就直接调用会抛异常。其次，假设没有异常：

这种情况，通知会丢失：

```
线程 A：发现条件不满足，准备等待
线程 B：修改条件，发送通知，但此时还没有线程在等待
线程 A：开始等待，错过了刚才的通知
```
