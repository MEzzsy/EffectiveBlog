# 线程安全概念

**什么是线程安全**

多个线程同时访问同一份数据时，程序仍能保证结果正确，不会因为执行顺序交错而出错。
例如：两个线程各给余额加 100，最终必须增加 200，不能丢掉其中一次更新。



**实现方法**

1. 互斥同步（悲观锁）
2. 非阻塞同步（乐观锁）
   1. CAS（Compare And Swap）指令
3. 无同步方案
   1. 可重入代码
   2. 线程本地存储

# 互斥同步

## 🌟synchronized

`synchronized` 是 Java 中的关键字。作用是用于互斥同步，通过对象锁，保证同一时刻只有一个线程执行同步代码。

### 加锁实现

Java 中每个对象都关联一个监视器（Monitor）。线程进入同步区域前获取对象锁，退出时释放锁，包括因为异常而退出。

- **锁谁**：实例同步方法锁 `this`；静态同步方法锁对应的 `Class` 对象；同步代码块锁括号里的对象。
- **可重入**：线程已经持有某个锁时，可以再次获取它；每次获取都需要对应一次释放。



字节码层面：

- 同步代码块使用 `monitorenter` / `monitorexit`
- 同步方法通过 `ACC_SYNCHRONIZED` 标志让 JVM 管理加锁和释放

它们最终都操作对象的 Monitor（监视器）。可以先把 Monitor 理解为记录着“谁持有锁、重入了几次”的机制。

**`monitorenter`：尝试获取锁。**

它从操作数栈取出锁对象的引用，然后：

- 没有线程持有锁：当前线程获得锁，计数设为 `1`。
- 当前线程已经持有锁：计数加 `1`，这就是可重入。
- 其他线程持有锁：当前线程需要等待，直到能够获得锁，才能继续执行后面的代码。

**`monitorexit`：释放一次锁。**

只有持有锁的线程才能执行释放，计数减 `1`：

- 计数仍大于 `0`：当前线程继续持有锁。
- 计数变成 `0`：真正释放锁，其他线程可以竞争。

所以，同一个线程加锁两次，就需要释放两次。编译器还会生成异常处理路径，确保同步代码块因为异常退出时，也会执行 `monitorexit`。

**`ACC_SYNCHRONIZED`：告诉 JVM“这个方法执行前必须获取锁”。**

它是方法上的一个标志位。JVM 调用方法时识别这个标志，自动完成：

```
确定锁对象 → 获取锁 → 执行方法体 → 正常返回或异常退出时释放锁
```

这些是 JVM 必须保证的行为规则；实际执行时，JVM 可以通过轻量级锁、自旋等方式减少开销。



### 锁优化

**为什么要锁优化**

加锁和解锁本身存在开销。锁竞争还可能导致线程阻塞与唤醒，而线程的阻塞和唤醒需要耗费很多的处理器时间。所以synchronized是Java语言中一个重量级的操作。



锁优化就是：**在保证线程安全的前提下，让没有竞争时的加锁更便宜，减少不必要的加锁和线程阻塞。**

主要有两类思路：

| 优化                  | 简单理解                                                     |
| --------------------- | ------------------------------------------------------------ |
| **轻量级加锁**        | 无竞争时，通过 CAS 等原子操作快速完成加锁，减少进入复杂监视器路径的开销 |
| **自旋 / 自适应自旋** | 暂时拿不到锁，先忙等一小会儿；如果锁很快释放，就省掉阻塞和唤醒的成本。自适应表示等待策略会根据运行情况调整 |
| **锁消除**            | JIT 证明某个对象不会被其他线程访问，就可能去掉其不必要的加锁 |
| **锁粗化**            | 连续多次对同一个对象加锁，JIT 可能合并成一次，减少反复加锁和解锁 |



#### 锁粗化

把连续的小同步区域合并成一个大同步区域。

原本是：

```
加锁 → 操作 A → 解锁
加锁 → 操作 B → 解锁
加锁 → 操作 C → 解锁
```

优化后：

```
加锁 → 操作 A → 操作 B → 操作 C → 解锁
```

这样，加锁和解锁从 3 次减少到 1 次，节省了重复操作的开销。前提是使用同一把锁，并且 JIT 判断合并不会破坏程序的正确性。

### 锁池和等待池

在java中，每个对象都有两个池，monitor（简单理解为锁池）和等待池。

-   锁池：假设线程A已经拥有了某个对象的锁，而其它的线程想要调用这个对象的某个synchronized方法(或者synchronized块)，由于这些线程在进入对象的synchronized方法之前必须先获得该对象的锁的拥有权，但是该对象的锁目前正被线程A拥有，所以这些线程就进入了该对象的锁池中。
-   等待池：假设一个线程A调用了某个对象的wait()方法，线程A就会释放该对象的锁后，进入到了该对象的等待池中



问题：为什么wait或者notify需要拿到锁？

首先没拿到锁就直接调用会抛异常。其次，假设没有异常：

这种情况，通知会丢失：

```
线程 A：发现条件不满足，准备等待
线程 B：修改条件，发送通知，但此时还没有线程在等待
线程 A：开始等待，错过了刚才的通知
```

## ReentrantLock

除了synchronized之外，还可以使用`java.util.concurrent`包中的重入锁（ReentrantLock）来实现同步。

相比synchronized，ReentrantLock增加了一些高级功能，主要有下面三个：

1. 等待可中断
   当持有锁的线程长期不释放锁的时候，正在等待的线程可以选择放弃等待，改为处理其他事情，可中断特性对处理执行时间非常长的同步块很有帮助。
2. 公平锁
   公平锁是指多个线程在等待同一个锁时，必须按照申请锁的时间顺序来依次获得锁；而非公平锁则不保证这一点，在锁被释放时，任何一个等待锁的线程都有机会获得锁。
   synchronized中的锁是非公平的，ReentrantLock默认情况下也是非公平的，但可以通过带布尔值的构造函数要求使用公平锁。
3. 锁可以绑定多个条件
   锁绑定多个条件是指一个ReentrantLock对象可以同时绑定多个Condition对象，而在synchronized中，锁对象的wait()和notify()或notifAII()方法可以实现一个隐含的条件，如果要和多于一个的条件关联的时候，就不得不额外地添加一个锁，而ReentrantILock则无须这样做，只需要多次调用newCondition方法即可。

## 两者区别

1. synchronized是jvm层面上实现的，而ReentrantLock是Java代码层面上实现的。
2. synchronized在发生异常时，会自动释放线程占有的锁，因此不会导致死锁现象发生；而Lock在发生异常时，如果没有主动通过unLock()去释放锁，则很可能造成死锁现象，因此使用Lock时需要在finally块中释放锁
3. Lock可以让等待锁的线程响应中断，而synchronized却不行，使用synchronized时，等待的线程会一直等待下去，不能够响应中断；
4. 通过Lock可以知道有没有成功获取锁，而synchronized却无法办到。
5. synchronized更容易优化，因为Java虚拟机可以在线程和对象的元数据中记录synchronized中锁的相关信息，而使用Lock的话，Java虚拟机是很难得知具体哪些锁对象是由特定线程锁持有的。

## ReentrantLock使用demo

### 等待可中断

```java
private static class WaitRunnable implements Runnable {
    /**
             * false：获取锁后sleep一段时间，模拟耗时操作
             * true：等待一段时间后就不获取锁
             */
    private final boolean tryWait;
    private final Lock lock;

    public WaitRunnable(boolean tryWait, Lock lock) {
        this.tryWait = tryWait;
        this.lock = lock;
    }

    @Override
    public void run() {
        if (tryWait) {
            try {
                if (lock.tryLock(1000, TimeUnit.MILLISECONDS)) {
                    try {
                        System.out.println("拿到锁");
                    } finally {
                        lock.unlock();
                    }
                } else {
                    System.out.println("等待超时，放弃获取锁");
                }
            } catch (InterruptedException e) {
                throw new RuntimeException(e);
            }
        } else {
            lock.lock();
            try {
                System.out.println("睡眠中");
                Thread.sleep(3000);
            } catch (InterruptedException e) {
                throw new RuntimeException(e);
            } finally {
                lock.unlock();
            }
            System.out.println("睡眠结束");
        }
    }
}

/**
         * 测试等待可中断
         */
public static void testTryLock() {
    final Lock lock = new ReentrantLock();
    Thread t1 = new Thread(new WaitRunnable(false, lock));
    Thread t2 = new Thread(new WaitRunnable(true, lock));

    t1.start();
    try {
        Thread.sleep(100);
    } catch (InterruptedException e) {
        throw new RuntimeException(e);
    }
    t2.start();
}
```

```
睡眠中
等待超时，放弃获取锁
睡眠结束
```

结论：通过tryLock方法来实现等待可中断的目的。

### 公平锁

```java
private static class FairRunnable implements Runnable {
    private final int id;
    private final Lock lock;

    public FairRunnable(int id, Lock lock) {
        this.id = id;
        this.lock = lock;
    }

    @Override
    public void run() {
        System.out.println("线程" + id + "开始，尝试获取锁");
        lock.lock();
        try {
            Thread.sleep(200);
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
        lock.unlock();
        System.out.println("线程" + id + "结束，释放锁");
    }
}

/**
         * 测试公平锁相关
         * 通过构造函数来设置是否是公平锁，默认非公平锁
         */
public static void testUnFairLock() {
    final Lock lock = new ReentrantLock();
    Thread t1 = new Thread(new FairRunnable(1, lock));
    Thread t2 = new Thread(new FairRunnable(2, lock));
    Thread t3 = new Thread(new FairRunnable(3, lock));

    t1.start();
    t2.start();
    t3.start();
}
```

线程1开始，尝试获取锁
线程3开始，尝试获取锁
线程2结束，释放锁
线程3结束，释放锁

结论：可以看到，默认情况下（非公平锁），获取锁的顺序是213，得到锁的顺序是231。

### 绑定多个条件

```java
private static class ConditionRunnable implements Runnable {
        public static void test() {
            final Lock lock = new ReentrantLock();
            Condition condition1 = lock.newCondition();
            Condition condition2 = lock.newCondition();

            Thread t1 = new Thread(new ConditionRunnable(true, lock, condition1, condition2));
            Thread t2 = new Thread(new ConditionRunnable(false, lock, condition1, condition2));

            t1.start();
            try {
                Thread.sleep(100);
            } catch (InterruptedException e) {
                throw new RuntimeException(e);
            }
            t2.start();
        }

        private final boolean firstLock;
        private final Lock lock;
        private final Condition condition1;
        private final Condition condition2;

        public ConditionRunnable(boolean firstLock,
                                 Lock lock,
                                 Condition condition1,
                                 Condition condition2) {
            this.firstLock = firstLock;
            this.lock = lock;
            this.condition1 = condition1;
            this.condition2 = condition2;
        }

        @Override
        public void run() {
            if (firstLock) {
                firstLock();
            } else {
                secondLock();
            }
        }

        private void firstLock() {
            lock.lock();
            try {
                try {
                    System.out.println("before condition1.await()");
                    condition1.await();
                    System.out.println("after condition1.await()");
                } catch (InterruptedException e) {
                    e.printStackTrace();
                }

                try {
                    System.out.println("before condition2.await()");
                    condition2.await();
                    System.out.println("after condition2.await()");
                } catch (InterruptedException e) {
                    e.printStackTrace();
                }
            } finally {
                lock.unlock();
            }
        }

        private void secondLock() {
            lock.lock();
            try {
                System.out.println("before condition1.notifyAll()");
                condition1.signalAll();
                System.out.println("after condition1.notifyAll()");

                System.out.println("before condition2.notifyAll()");
                condition2.signalAll();
                System.out.println("after condition2.notifyAll()");
            } finally {
                lock.unlock();
            }
        }
    }
}
```

```
before condition1.await()
before condition1.notifyAll()
after condition1.notifyAll()
before condition2.notifyAll()
after condition2.notifyAll()
after condition1.await()
before condition2.await()
```

注意，以上代码会导致死锁！！！

结论：

1.   Condition通过lock构建，作用和使用方式类似Object的wait和notify。
2.   为什么Condition的方法名称不叫wait和notify？因为wait和notify是Object的方法，所有对象类型都是继承Object。
3.   lock虽然可以绑多个Condition，但是代码变得复杂，很容易导致一直拿不到锁，如上面demo的代码。
     首先线程1拿到锁，并且wait condition1，释放锁并进入等待池。
     接着线程2拿到锁，并且连续notifyAll condition1和condition2。
     当线程2释放锁后，等待池中的condition1进入锁池并拿到锁，但是接着wait condition2。
     这个时候就没有线程notifyAll condition2，线程1一直在等待。

### 实现原理

`ReentrantLock` 底层基于 AQS（AbstractQueuedSynchronizer，抽象队列同步器），核心是：用状态记录锁，用 CAS 竞争锁，用队列管理等待线程。

它主要维护三样东西：

- **`state`**：`0` 表示未被持有，大于 `0` 表示持有次数。
- **持有线程**：记录当前是谁拿着锁。
- **同步队列**：保存竞争锁失败、需要等待的线程。

整个过程可以这样理解：

1. **加锁**
   锁空闲时，线程尝试通过 CAS 将 `state` 从 `0` 改成 `1`。成功就拿到锁，并记录自己是持有者。
2. **重入**
   如果锁已经被自己持有，就将 `state + 1`，直接进入。这就是“可重入”的实现原理。
3. **等待**
   如果锁被其他线程持有，调用 `lock()` 的线程会进入 AQS 同步队列，必要时通过 `LockSupport.park()` 阻塞。
4. **解锁**
   每次 `unlock()` 将 `state - 1`。减到 `0` 才真正释放锁，随后唤醒合适的等待线程，让它重新尝试获取锁。****被唤醒不代表已经拿到锁**。** 

公平与非公平，主要区别在于新线程能不能插队：

- **非公平锁（默认）**：新线程可以直接尝试抢锁。
- **公平锁**：非重入获取时，会检查是否有排在前面的等待线程，让先等待的线程优先获取。无参 `tryLock()` 是例外，它不遵守公平设置。

# CAS

CAS（Compare And Swap，比较并交换）是一种原子操作：比较变量的当前值与预期值，相同就更新，否则不更新。

例如，线程想把 `count` 从 `5` 改成 `6`：

```
当前值是 5 → 符合预期 → 更新为 6，成功
当前值是 7 → 不符合预期 → 不更新，失败
```

比较和更新是不可分割的整体，其他线程无法插入这两个步骤之间。

它常用于 `AtomicInteger`、锁的竞争等场景。更新失败后，程序可以读取最新值，再尝试更新。



CAS 底层依靠 CPU 提供的原子指令实现。

调用过程可以简化为：

```
Java 的 CAS 方法 → JVM → CPU 原子指令
```

以 x86 为例，通常使用 `LOCK CMPXCHG`：

- `CMPXCHG`：比较内存中的值与预期值，相同就写入新值。
- `LOCK` 前缀：保证这个“比较并更新”过程在多核环境下具有原子性，其他核心不能在中间插入对该位置的修改。

这里的 `LOCK` 是 CPU 指令前缀，不表示获取 Java 对象锁，也不需要因此把线程挂起。
