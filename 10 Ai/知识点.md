# 基础与概念

## 1. 什么是 AI Agent？它与传统聊天机器人、工作流自动化工具的核心区别是什么？

> - AI Agent以大语言模型为核心，给定任务后能够调用工具、自己决定下一步，直到完成目标或触发停止条件。
> - 传统聊天机器人主要负责对话。
> - 工作流自动化工具只能按预设步骤执行。

AI Agent 是一种以目标为驱动的软件系统。它以大语言模型或其他决策模型作为核心，根据当前环境和任务状态进行推理与规划，自主选择工具、执行操作、观察结果，并在必要时调整后续行动，直到完成目标或触发停止条件。

三者的核心区别在于决策方式和自主程度：

- 传统聊天机器人主要进行单轮或多轮语言交互，通常负责生成回答，不一定能够操作外部系统，也不一定维护明确的任务状态。
- 工作流自动化工具按照预先编排好的固定节点和条件分支执行，路径确定、可预测性强，但难以处理开发者没有预先枚举的情况。
- AI Agent 的执行路径通常不是完全固定的。它能够根据中间结果动态决定下一步，例如先检索资料，再判断是否需要调用计算工具，最后根据结果修正方案。

因此，Agent 的关键不只是“使用了 LLM”，而是形成了“观察—决策—行动—反馈”的闭环。不过工程中的 Agent 并不意味着无限自主，通常仍需要权限边界、预算、超时、审批和人工接管机制。

## 2. 一个典型 AI Agent 的关键组成模块有哪些？各模块之间如何协作？

> 一个 Agent 通常包括模型、规划、工具、记忆、状态管理这些模块。简单说，就是模型先理解目标并决定下一步，系统检查这个动作能不能做，然后调用工具，把结果再交给模型判断。这个过程循环进行，直到任务完成或达到停止条件。

一个典型 AI Agent 通常包含以下模块：

- **目标与指令模块**：定义 Agent 的角色、目标、约束、成功条件和停止条件。
- **模型模块**：理解用户意图，进行推理、规划、工具选择和结果总结。
- **规划与状态管理模块**：拆解任务，记录当前步骤、已完成工作、待办事项和执行状态。
- **工具模块**：封装搜索、数据库、代码执行、文件系统、业务 API 等外部能力。
- **记忆与知识模块**：保存当前会话信息、历史经验、用户偏好，并通过 RAG 等方式检索外部知识。
- **执行与编排模块**：负责调用模型和工具、处理超时与重试、控制循环以及协调各模块。
- **安全与权限模块**：进行身份认证、参数校验、权限检查、敏感信息过滤和高风险操作审批。
- **可观测与评估模块**：记录模型调用、工具调用、执行轨迹、延迟、成本和任务结果。

协作流程通常是：系统先接收用户目标和环境信息，模型结合记忆生成计划或下一步动作；编排器校验动作后调用相应工具；工具结果作为新的观察写入状态；模型再根据新状态继续执行、重新规划或结束任务。安全和可观测模块贯穿整个过程，而不是只在最后介入。

## 3. ReAct、Plan-and-Execute 和多 Agent 协作模式分别适用于什么问题？

> - ReAct 是边想边做，适合步骤不确定、需要不断看结果再决定下一步的任务。
> - Plan-and-Execute 是先列计划再执行，适合流程较长、步骤依赖比较清楚的任务。
> - 多 Agent 是让不同 Agent 分工，适合需要并行处理或多个专业角色的复杂任务，但成本和协作难度也更高。
> - codex的工作模式是[Agent Loop](./01 Codex 型通用 Agent 的工作方式.md)

### ReAct

ReAct 适合“事先无法确定完整路径”的问题。它的工作方式类似：

```
观察现状 → 采取行动 → 查看结果 → 调整判断 → 再行动
```

适用场景：

- 调试未知原因的 Bug
- 排查 CI、构建或部署失败
- 探索陌生代码库
- 操作网页、终端或外部工具
- 数据质量检查
- 需要反复试验的性能优化
- 测试失败后自动定位并修复

例如：

```
登录接口偶尔返回 500，请复现问题、查看日志、提出假设，
通过测试逐个验证，找到原因后修复并运行回归测试。
```

这里不能预先写死完整步骤，因为每一步都依赖实际观察结果。

不太适合：

- 路径已经非常明确的机械修改
- 一次性批量转换
- 必须严格遵循固定审批流程的任务

ReAct 的主要风险是“走一步看一步”可能导致方向漂移、重复尝试或消耗较多上下文。因此最好同时规定终止条件：

```
每个假设最多验证一次；连续三次没有新证据时停止并汇报。
```



### Plan-and-Execute

Plan-and-Execute 适合“步骤多、依赖复杂，但整体目标相对明确”的问题。

其工作方式是：

```
分析目标 → 制定计划 → 确认依赖和风险 → 逐项执行 → 验证整体结果
```

适用场景：

- 大型重构
- 框架或数据库迁移
- 跨模块功能开发
- API 版本升级
- 安全整改
- 从需求到实现的完整开发任务
- 需要多人审核或阶段性确认的工作
- 容易改漏文件的系统性修改

例如：

```
将身份认证从 Session 迁移到 JWT，先分析影响范围并制定迁移计划，
计划确认后再实施，保证迁移期间旧客户端仍然可用。
```

这种任务必须先弄清：

- 哪些模块受影响
- 步骤之间的依赖
- 如何保持兼容
- 如何迁移数据
- 如何测试和回滚

不太适合：

- 目标本身还不明确的探索性问题
- 每一步都高度依赖实时结果的问题
- 只有一两个简单步骤的修改

它的主要风险是“计划建立在错误假设上”。所以执行过程中不能机械照搬计划，应允许根据新证据更新计划：

```
如果实际代码与计划假设冲突，暂停当前步骤，更新计划后再继续。
```

### 多 Agent 协作

多 Agent 适合“可以拆成多个相互独立或弱依赖子任务”的问题。

其工作方式是：

```
主 Agent 分解任务
   ├─ Agent A：子任务 A
   ├─ Agent B：子任务 B
   └─ Agent C：子任务 C
          ↓
主 Agent 汇总、解决冲突并验证
```

适用场景：

- 大型代码库并行探索
- PR 多维度审查
- 多个相互独立模块的分析
- 安全、性能、测试分别审计
- 大量文档或日志的分片分析
- 多方案并行研究和比较
- 多个平台或多种实现的验证
- 测试、文档、代码审查等辅助工作并行执行

例如：

```
并行审查当前 PR：

- Agent A 检查安全风险；
- Agent B 棩查逻辑错误和并发问题；
- Agent C 检查测试覆盖；
- Agent D 检查性能和可维护性。

等待全部完成后，由主 Agent 去重、核验证据并按严重程度汇总。
```

不太适合：

- 强顺序依赖的任务
- 多个 Agent 必须频繁修改同一文件
- 无法清晰划分责任边界的问题
- 很小的任务
- 需要单一、一致设计判断的核心实现

多 Agent 并不天然比单 Agent 更好。主要成本包括：

- Token 使用量更大
- 结果可能重复或矛盾
- 多个 Agent 同时写代码可能发生冲突
- 主 Agent 需要额外验证和整合

因此，多 Agent 最适合并行执行“读多写少”的工作，例如探索、检索、测试、审查和日志分析。写代码时最好让不同 Agent 负责不同模块，或者只让一个主 Agent 落地修改。

### 如何选择

可以用三个问题快速判断：

1. 下一步是否取决于刚得到的结果？
   - 是：优先 ReAct。
2. 是否存在较长且明确的步骤依赖？
   - 是：优先 Plan-and-Execute。
3. 是否能拆出两个以上相互独立的子任务？
   - 是：考虑多 Agent。

典型选择如下：

- 未知 Bug：ReAct
- 跨系统迁移：Plan-and-Execute
- 大型 PR 审查：多 Agent
- 小范围明确修改：普通单 Agent 直接执行
- 大型未知故障：先 Plan-and-Execute 划分调查方向，再让多个 Agent 并行调查，每个 Agent 内部使用 ReAct

实践中最强的往往是组合模式：

```
Plan-and-Execute 负责全局方向
        ↓
多 Agent 负责并行分工
        ↓
每个 Agent 用 ReAct 处理不确定细节
        ↓
主 Agent 汇总、实施并验证
```

一句话概括：

- ReAct 擅长处理“不确定性”。
- Plan-and-Execute 擅长处理“依赖性”。
- 多 Agent 擅长处理“可并行性”。

### codex和上述三种模式的关系

**Agent Loop 与 ReAct 的关系**

- Codex Agent Loop 与 ReAct 思想非常接近。但 OpenAI 官方使用的名称是 Agent Loop，不保证它严格复现某篇 ReAct 论文的提示格式或内部轨迹。



**Agent Loop 与 Plan-and-Execute 的关系**

Agent Loop 解决的是“如何持续行动和反馈”，Plan-and-Execute 解决的是“如何组织一个较长任务”。二者不是互斥关系。一个完整的 Plan-and-Execute 工作流可以表示为：

```text
Plan 阶段
  Agent Loop：读取 → 搜索 → 提问 → 更新计划
        ↓
计划确认
        ↓
Execute 阶段
  Agent Loop：修改 → 测试 → 观察 → 修正 → 验证
```

即使先制定了计划，执行阶段仍然需要 Agent Loop。计划提供全局方向，循环负责处理执行中出现的新事实。



**Agent Loop 与多 Agent 的关系**

多 Agent 是在单个 Agent Loop 之上增加并行编排。主 Agent 可以把相互独立的任务交给多个子 Agent，每个子 Agent 都运行自己的循环，最后由主 Agent 收集结果。



## Agent 的「感知、规划、行动、记忆」分别指什么？

> - 感知就是读取用户输入和环境信息；
> - 规划是判断要做什么、分几步做；
> - 行动是实际调用工具或系统；
> - 记忆是保存当前状态和有用的历史信息。
>
> 它们会形成一个循环：先获取信息，再做计划、执行动作，然后根据新结果继续调整。

- **感知**：接收并理解来自用户和环境的信息，例如自然语言、图像、网页内容、数据库结果、工具错误和系统状态。感知不仅是读取数据，还包括把原始输入转换成可用于决策的结构化状态。
- **规划**：根据目标、约束和当前状态确定后续步骤，包括任务拆解、工具选择、依赖排序、风险判断以及成功和停止条件。
- **行动**：执行计划中的具体操作，例如调用 API、查询数据库、修改文件、发送请求或向用户提问。行动前通常需要经过参数校验和权限检查。
- **记忆**：保存和检索对任务有用的信息。短期记忆维护当前会话和任务状态，长期记忆保存经过筛选的历史事实、经验或用户偏好，外部知识库则提供可检索的领域资料。

这四部分构成一个循环：Agent 感知环境，结合记忆进行规划，执行行动，再感知行动结果并更新记忆和计划。系统的可靠性很大程度上取决于这个闭环是否有清晰的状态、校验和停止机制。



## 如何判断一个任务适合交给 Agent，而不是通过固定流程或单次 LLM 调用完成？

> 主要看任务是不是需要多步决策，以及中间结果会不会影响后续步骤。
>
> 如果只是摘要、分类这类一次调用就能完成的任务，用 LLM 就够了；
>
> 如果步骤固定，就用普通工作流；
>
> 如果路径不确定、要连续调用工具并根据结果调整，才比较适合 Agent。高风险任务还要加人工确认。

可以从任务的不确定性、步骤数量、外部交互和风险四个方面判断。

适合使用 Agent 的任务通常具有以下特征：目标明确但执行路径难以预先穷举；需要多步推理和连续工具调用；中间结果会影响下一步决策；需要处理非结构化信息或异常情况；任务可以通过反馈逐步修正。例如跨来源调研、复杂故障排查和代码修复。

如果输入到输出只需要一次理解、生成、分类或抽取，通常单次 LLM 调用更简单，例如摘要、改写和情感分类。如果业务步骤固定、规则明确且强调稳定性与审计，则更适合确定性工作流，例如审批流、定时同步和标准化数据处理。

还要考虑风险与收益。即使任务具有不确定性，只要错误后果很严重且难以回滚，也不应直接给予 Agent 完整执行权。可以采用“Agent 生成建议或计划，确定性程序执行，关键节点人工审批”的混合方案。



## LLM 在 Agent 系统中常见的职责有哪些？哪些职责不应完全依赖 LLM？

> LLM 适合做意图理解、任务拆解、工具选择和结果总结，因为这些事情需要处理自然语言和不确定性。但权限校验、金额限制、精确计算、事务控制和高风险操作授权不能只靠 LLM，应该交给代码、规则引擎或人工审批。简单说，LLM 负责灵活判断，程序负责守住硬规则。

LLM 擅长处理语义和不确定性，因此常用于理解用户意图、提取任务约束、拆解任务、选择工具、生成工具参数、解释工具结果、处理自然语言以及根据反馈调整计划。它也适合在多个合理方案之间进行启发式选择。

以下职责不应完全依赖 LLM：

- **身份认证和权限控制**：必须由确定性的安全系统执行。
- **参数及业务规则校验**：例如金额上限、数据类型、库存约束和合规规则，应由代码或规则引擎验证。
- **精确计算和事实查询**：应交给计算器、数据库或权威数据源，不能依赖模型记忆。
- **事务、幂等和并发控制**：应由应用和基础设施保障。
- **敏感操作的最终授权**：删除数据、付款、退款和对外发送等操作需要明确审批或强约束。
- **停止条件、预算和超时**：应由编排器硬性执行，不能只通过提示词要求模型自觉遵守。

总体原则是：让 LLM 负责理解、生成和软决策，让确定性系统负责安全边界、精确规则和最终执行保障。



## 什么是工具调用（Tool Calling / Function Calling）？如何设计可靠的工具描述和参数模式？

> 工具调用就是模型按照定义好的格式，告诉应用它想调用哪个工具、传什么参数，真正的执行还是由应用完成。工具设计要做到职责单一、名称和描述清楚、参数类型和必填项明确。服务端还必须再次校验参数和权限，写操作最好支持预览、确认和幂等。

工具调用是指向模型提供一组可用工具及其参数定义，让模型根据任务生成结构化的调用请求。应用程序接收请求后进行校验和授权，真正执行函数或外部 API，再将执行结果返回给模型。模型提出工具调用并不等于模型本身执行了工具。

可靠的工具设计应注意以下几点：

- 工具名称应明确表达单一职责，避免一个工具承担过多互不相关的操作。
- 描述要说明工具能做什么、不能做什么、何时使用，以及与相似工具的区别。
- 参数使用严格 Schema，明确类型、必填项、枚举、格式、取值范围和默认行为。
- 避免含义模糊的布尔参数，优先使用语义清晰的枚举，例如将 `force: true` 改成明确的执行模式。
- 将高风险的读操作和写操作拆成不同工具，并让写操作支持预览、确认、幂等键和审计。
- 工具结果应采用稳定的结构，包含状态、数据、错误码、可重试标志和必要的来源信息。
- 服务端必须重新校验模型生成的所有参数，并基于当前用户身份执行权限检查。

此外，应该用正常输入、歧义输入、缺失参数、越权请求和工具失败等测试用例评估工具选择与参数生成，而不能只验证理想路径。



## 什么是结构化输出？如何降低模型输出不符合 Schema 的概率？

> 结构化输出就是让模型按固定格式返回数据，比如符合 JSON Schema 的 JSON，方便程序直接解析。要提高成功率，最好使用模型原生的结构化输出能力，同时把 Schema 设计得简单明确。应用端仍然要做格式和业务校验，失败后可以有限重试，不能认为格式正确就代表内容一定正确。

结构化输出是让模型按照预先定义的数据结构返回结果，例如满足 JSON Schema 的 JSON 对象，而不是返回自由文本。它便于程序解析、校验、存储和驱动后续流程，常用于信息抽取、分类、工具参数生成和 Agent 间通信。

降低不符合 Schema 概率的方法包括：

- 优先使用模型或平台提供的原生结构化输出能力，而不只是提示模型“返回 JSON”。
- 让 Schema 尽量简单明确，限制不必要的嵌套、联合类型和自由格式字段。
- 为字段提供清晰描述，合理使用必填项、枚举、数值范围和格式约束。
- 在提示中给出业务规则以及少量正确示例，但不能依靠示例代替 Schema。
- 在应用侧执行语法和语义两层校验；语法正确的 JSON 仍可能违反业务规则。
- 校验失败时，将具体错误反馈给模型进行有限次数的修复，超过次数后降级或转人工。
- 对关键字段使用确定性程序补充验证，例如检查资源是否存在、用户是否有权限、日期范围是否合法。

需要注意，结构化输出只能提高格式可靠性，不能保证内容事实正确或操作安全。



## 什么是结构化输出？

结构化输出（Structured Output）是指让模型按照预先定义的、机器可解析的数据结构返回结果，而不是生成自由文本。

例如，希望 Agent 判断用户意图并返回：

```
{
  "intent": "search",
  "query": "北京天气",
  "confidence": 0.95
}
```

对应的 JSON Schema 可以是：

```
{
  "type": "object",
  "properties": {
    "intent": {
      "type": "string",
      "enum": ["search", "order", "other"]
    },
    "query": {
      "type": ["string", "null"]
    },
    "confidence": {
      "type": "number",
      "minimum": 0,
      "maximum": 1
    }
  },
  "required": ["intent", "query", "confidence"],
  "additionalProperties": false
}
```

它主要用于：

- 生成函数或工具的调用参数
- 从文档中抽取字段
- 意图分类
- 将结果保存到数据库
- 驱动前端组件或后续工作流
- 在多个 Agent 之间传递状态

要注意，结构化输出包含两个不同层面：

1. **结构正确**：JSON 能解析，字段和类型符合 Schema。
2. **语义正确**：字段中的内容符合真实情况和业务规则。

例如 `confidence: 99` 不符合上面的 Schema；而 `confidence: 0.9` 虽然符合 Schema，却不一定是一个合理、可信的判断。





## 三种实现方式

可靠性通常从低到高排列如下：

| 方式                               | 能保证什么                 | 可靠性 |
| ---------------------------------- | -------------------------- | ------ |
| Prompt 要求“只返回 JSON”           | 什么也不严格保证           | 低     |
| JSON Mode                          | 通常保证是合法 JSON        | 中     |
| Structured Outputs + strict Schema | 约束字段、类型、枚举和结构 | 高     |

如果模型平台支持原生 Structured Outputs，应优先使用 `json_schema` 和严格模式，而不是只在 Prompt 中粘贴 Schema。OpenAI 官方将 JSON Mode 视为较旧方案，并推荐支持时使用 `json_schema`；严格模式只支持 JSON Schema 的一个子集。[OpenAI API Reference](https://platform.openai.com/docs/api-reference/evals/run-output-item-object)

对于 Agent：

- **最终回答需要固定格式**：使用 Structured Outputs。
- **模型需要调用工具**：使用 Function Calling，并为工具参数开启严格 Schema。
- **不要让模型先生成一段 JSON 文本，再用正则表达式提取工具参数。**

## 如何降低不符合 Schema 的概率？

### 优先使用生成阶段的强约束

最有效的方法是使用平台原生的约束生成能力：

```
response_format = json_schema
strict = true
```

或者为函数调用参数设置严格模式。

这种能力通常会在模型生成每个 token 时限制可选范围，效果明显好于“生成完以后再解析”。

但仍然要处理以下非正常完成情况：

- 输出达到 token 上限而被截断
- 模型拒绝回答
- 内容安全策略中断生成
- Schema 使用了平台不支持的关键字
- 请求超时或服务端错误

因此，“严格模式”不能替代应用层错误处理。

### 简化 Schema

Schema 越深、分支越多，模型越容易出错，平台也可能直接拒绝过于复杂的 Schema。

建议：

- 减少不必要的嵌套
- 避免大量 `anyOf`、`oneOf` 和条件 Schema
- 用 `enum` 代替含糊的自由文本
- 能用固定字段时，不使用动态 key
- 明确设置 `required`
- 使用 `additionalProperties: false`
- 不确定的值使用 `null`，不要让模型擅自省略字段
- 为字段提供清晰的 `description`
- 只使用当前模型平台明确支持的 Schema 子集

例如，与其设计：

```
{
  "result": {
    "data": {
      "classification": {
        "value": "positive"
      }
    }
  }
}
```

不如直接设计：

```
{
  "sentiment": "positive"
}
```

Google 的官方文档同样说明，Structured Outputs 只支持 JSON Schema 的一个子集，过大或嵌套过深的 Schema 可能被拒绝。[Gemini Structured Outputs](https://ai.google.dev/gemini-api/docs/structured-output?lang=rest)

### 消除 Prompt 和 Schema 的冲突

下面的指令容易造成冲突：

```
请详细解释判断过程。
最终只返回符合 Schema 的 JSON。
```

如果 Schema 中没有 `explanation` 字段，模型可能在 JSON 前后输出解释文字。

更稳妥的写法是：

```
分析用户输入并填充给定 Schema。
不要添加 Schema 之外的字段。
无法确定的字段填写 null。
```

如果确实需要解释，就把它定义为字段：

```
{
  "result": "approved",
  "reason": "符合审批条件"
}
```

### 明确缺失值和异常值策略

模型不知道某个字段时，可能会：

- 省略字段
- 返回空字符串
- 返回 `"unknown"`
- 返回 `null`
- 编造一个值

必须明确统一策略，例如：

```
没有相关信息时返回 null，不要猜测，不要省略字段。
没有匹配项时返回空数组 []。
```

这类规则最好同时体现在 Schema 中：

```
{
  "type": ["string", "null"]
}
```

### 使用强类型和有限取值

相比自由字符串：

```
{
  "status": {
    "type": "string"
  }
}
```

下面的定义更稳定：

```
{
  "status": {
    "type": "string",
    "enum": ["pending", "approved", "rejected"]
  }
}
```

同理，布尔值应该用 `boolean`，数量应该用 `integer`，不要全部定义成字符串。

### 合理设置生成参数

降低 `temperature` 可以减少随机性，对 Prompt-only JSON 和语义稳定性有帮助，例如设置为 `0`～`0.2`。

但要注意：

- 低温度不能保证 Schema 合规。
- 原生约束解码比调整温度有效得多。
- 不要同时频繁调整 `temperature` 和 `top_p`。

### 预留足够的输出长度

如果 `max_output_tokens` 太小，模型可能在 JSON 中间被截断：

```
{
  "users": [
    {"name": "Alice"},
    {"name":
```

因此应该：

- 根据最大数组长度估算 token 上限
- 限制 `maxItems`
- 控制自由文本字段的长度
- 检查响应的结束原因
- 将“输出截断”与“Schema 校验失败”分开统计

### 在应用层进行双重校验

即使使用严格模式，仍应执行两层校验：

```
模型输出
  → JSON 解析
  → Schema 校验
  → 业务语义校验
  → 执行工具或保存数据
```

可以使用：

- Python：Pydantic、jsonschema
- TypeScript：Zod、Ajv
- Java：Jackson、Bean Validation

业务语义校验包括：

- `start_time` 是否早于 `end_time`
- 商品 ID 是否真实存在
- 金额是否超过账户余额
- 枚举组合是否合法
- 模型生成的 URL、文件路径或 SQL 是否安全

官方文档也特别指出：结构化输出能够约束 JSON 结构，但不能保证字段值在语义上正确，因此仍需应用层验证。[Google Structured Outputs best practices](https://ai.google.dev/gemini-api/docs/structured-output?lang=rest)

### 校验失败后进行定向重试

不要只重复发送完全相同的请求。应该把校验错误反馈给模型：

```
上次输出未通过校验：

- 缺少必填字段 query
- confidence 必须位于 0 到 1 之间
- 不允许字段 explanation

请根据原始输入重新生成完整结果。
```

推荐最多重试 1～3 次，并使用以下策略：

1. 第一次：正常生成。
2. 第二次：携带具体校验错误重新生成。
3. 第三次：使用更强模型或更简单的 Schema。
4. 仍然失败：返回显式错误或进入人工处理流程。

不要默默删除未知字段、强制转换所有类型，因为这可能掩盖真实的语义错误。

### 建立评测和监控

生产环境至少记录：

- JSON 解析成功率
- Schema 校验通过率
- 语义校验通过率
- 重试率
- 截断率
- 拒绝率
- 各字段错误分布
- 模型、Prompt 和 Schema 版本

用真实输入建立测试集，尤其覆盖：

- 字段缺失
- 输入存在歧义
- 超长文本
- 多语言输入
- Prompt 注入
- 空结果
- 大数组
- 特殊字符与转义字符

## 最实用的原则

可以概括成一句话：

> 使用平台原生的严格 Structured Outputs，保持 Schema 简单明确，并在应用层执行 Schema 校验、业务校验和有限次数的定向重试。

其中优先级是：

```
原生严格约束
> 简化并明确 Schema
> 应用层校验与重试
> 清晰 Prompt 和示例
> 降低 temperature
> 仅靠“请返回 JSON”
```

另外，即使 Schema 合规，也不要直接执行高风险操作。涉及付款、删除数据、发送消息或修改权限时，应把结构化结果当作“候选操作参数”，继续执行权限检查、业务校验和必要的用户确认。





## 9. Agent 的自主性应如何定义和约束？

Agent 的自主性可以定义为：在多大范围内，它能够在没有逐步人工指令的情况下，自行决定目标的执行路径、选择工具并实施操作。自主性不是简单的“开启或关闭”，而是由多个维度共同决定，包括可访问的数据、可用工具、操作权限、执行时间、成本预算、是否允许对外产生影响以及哪些步骤需要审批。

约束自主性通常采用分层机制：

- 通过明确的目标、范围和完成标准限制任务边界。
- 根据最小权限原则，只授予当前任务必需的数据和工具权限。
- 将只读、可逆写入和不可逆操作划分不同风险等级。
- 对高风险操作设置预览、二次确认、人工审批或双人复核。
- 使用确定性的参数校验、策略引擎和沙箱，而不是只依赖系统提示词。
- 设置最大步数、超时、调用配额、费用上限、重试次数和紧急停止开关。
- 保存完整审计轨迹，并提供回滚、补偿和人工接管能力。

合理的设计原则是让自主程度与任务风险匹配：风险越低、操作越可逆、验证越充分，Agent 可以拥有越高自主性；风险越高，则越需要确定性约束和人类在环。

**口语版回答：** 自主性就是 Agent 能在多大范围内自己决定怎么做、调用什么工具，以及能不能直接执行。约束它时要遵循最小权限原则，再加上最大步数、超时、预算、参数校验和审计。查询类、可回滚的操作可以更自动化，付款、删除这类高风险操作则必须人工确认。

## 10. 如何解释 Agent 的确定性、可控性与灵活性之间的权衡？

**确定性**是指相同输入在相同状态下得到一致执行路径和结果的程度；**可控性**是指系统能否把行为限制在权限、规则、预算和业务目标范围内；**灵活性**是指系统面对新情况、模糊需求和非预期中间结果时调整策略的能力。

固定规则和预编排工作流具有较高确定性与可控性，但只能处理预先定义的路径。由 LLM 动态决策的 Agent 灵活性更强，却可能产生不同计划、错误参数、幻觉或不可预测的调用链。三者通常无法同时最大化。

工程上常用混合架构取得平衡：让 LLM 负责意图理解、方案生成和低风险决策；让状态机、Schema、权限系统、策略引擎和业务代码控制执行边界；对关键操作增加审批；用评测集、监控和审计持续验证结果。还可以按任务风险动态调整自主性，例如低风险查询允许自动执行，高风险写操作只允许 Agent 生成计划并等待确认。

因此，目标不是让 Agent 的每一步都完全确定，而是让其变化发生在可接受、可验证、可追溯和可恢复的范围内。

**口语版回答：** 固定规则最确定、最好控制，但遇到预设之外的情况就不够灵活；LLM 驱动的 Agent 更灵活，但结果和执行路径可能不稳定。实际工程里一般采用混合方式：让 LLM 处理理解和决策，让工作流、权限系统和规则代码控制边界。目标不是完全消除不确定性，而是让不确定性可验证、可追踪、可回滚。
