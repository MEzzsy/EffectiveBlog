# 前置知识：suspend

## 🌟kotlin编译器处理

Kotlin 编译器处理 `suspend` 函数时，主要做四件事：

1. **增加续体参数**：隐式传入 `Continuation`，用于交付后续结果。
2. **调整返回类型**：在 JVM 上返回 `Object`，兼容正常结果和 `COROUTINE_SUSPENDED` 挂起标记。
3. **按需生成状态机**：分析当前suspend函数内部的潜在挂起点（即是否调用了suspend函数），用 `label` 记录恢复位置，保存跨挂起点需要的局部变量。
4. **生成执行分支**：同步完成就继续执行；返回挂起标记就退出当前执行，恢复后从对应位置继续。

## 隐式传入 Continuation

编译器既会修改挂起函数的签名，也会修改调用它的位置。下面是**原理伪代码**，省略函数体：

```kotlin
// 业务代码中的声明。
suspend fun readText(id: Int): String

// 编译后的签名示意：追加 Continuation，返回类型改成 Any?（JVM 上是 Object）。
fun readText(id: Int, completion: Continuation<String>): Any?
```

调用处也由编译器自动补上这个参数：

```kotlin
// 业务代码：位于挂起函数或挂起 Lambda 中。
val text = readText(1)

// 编译后的调用片段：位于调用者的状态机中。
label = 1
val result = readText(1, completion = this)
if (result === COROUTINE_SUSPENDED) return COROUTINE_SUSPENDED
val text = result as String // 同步完成时，直接取得结果。
```

这里的 `this` 是**调用者的续体对象**，保存着调用者的恢复位置。若 `readText` 真正挂起，稍后会通过传入的续体交付结果或异常，让调用者继续执行；若同步完成，则直接返回结果，无需再恢复这个续体。完整的恢复分支见下一节。

### 🌟Continuation介绍

```kotlin
public interface Continuation<in T> {
    public val context: CoroutineContext
    public fun resumeWith(result: Result<T>)
}
```

简单理解：协程体可能会调用suspend方法（这个suspend方法可能会有返回值）而挂起。恢复后，返回值（也可能是异常）通过Continuation来传递，让协程继续执行。

## 简单代码说明

```kotlin
scope.launch { // 外层挂起 Lambda，Context 中的调度器是 Main。
    val title = "读取结果"
    Log.d(TAG, "1：开始，线程：${Thread.currentThread().name}")

    val result = withContext(Dispatchers.IO) { // 内层挂起 Lambda。
        Log.d(TAG, "2：读取，线程：${Thread.currentThread().name}")
        delay(1_000)
        "协程读取完成"
    }

    Log.d(TAG, "3：$title / $result，线程：${Thread.currentThread().name}")
    Toast.makeText(context, result, Toast.LENGTH_SHORT).show()
}
```

外层可用下面的**原理伪代码**理解。以下字段和方法都属于外层续体对象：`resumeWith` 是恢复入口，简化自标准库基类的实现；`invokeSuspend` 是编译器生成的状态机。这里省略调度、取消检查和部分实现细节。

对象保存的 `completion` 是 `launch` 创建的协程对象，用于接收外层协程体的最终结果；调用 `withContext` 时传入的 `completion = this` 则是外层续体自身，用于接收内层结果。后者是编译器补入的隐藏参数，不是业务可直接调用的重载。

```kotlin
var label = 0
var savedTitle: String? = null

fun resumeWith(resumed: Result<Any?>) {
    val outcome: Result<Unit> = try {
        val value = invokeSuspend(resumed) // 根据 label 开始或继续执行。
        if (value === COROUTINE_SUSPENDED) return // 再次挂起，等待下一次恢复。
        Result.success(Unit) // 本例的外层协程体执行完毕，返回 Unit。
    } catch (e: Throwable) {
        Result.failure(e)
    }
    completion.resumeWith(outcome) // 把外层协程体的最终结果交给协程对象。
}

fun invokeSuspend(resumed: Result<Any?>): Any? {
    val input = resumed.getOrThrow() // 恢复结果为失败时，在这里抛出。
    val output: Any?

    when (label) {
        0 -> {
            savedTitle = "读取结果"
            执行代码1()

            label = 1 // 调用可能挂起的函数之前，先设置恢复位置。
            output = withContext(IO, 内层Lambda, completion = this)
            if (output === COROUTINE_SUSPENDED) {
                return COROUTINE_SUSPENDED
            }
            // 若同步完成，直接携带 output 执行后面的代码。
        }

        1 -> {
            output = input // 恢复时得到 withContext 的结果。
        }

        else -> error("非法状态")
    }

    val result = output as String
    执行代码3(savedTitle, result)
    return Unit
}
```

以 `withContext` 真正挂起、随后成功完成为例，恢复过程可简化为：

```kotlin
// 首次启动：调度到 Main 后，进入 label = 0。
外层续体.resumeWith(Result.success(Unit))

// withContext 挂起后完成：结果调度回 Main，再进入 label = 1。
外层续体.resumeWith(Result.success("协程读取完成"))
// 如果失败，则通过 Result.failure(exception) 交付异常。
```

第一次进入时 `label = 0`，执行代码 1，然后先写入 `label = 1`。如果 `withContext` 返回挂起标记，`invokeSuspend` 也返回这个标记，`resumeWith` 随即退出，暂时不会执行代码 3，也不会通知 `completion` 外层协程体已完成。

下一次调用 `resumeWith` 时，`label` 仍然是 1，状态机取得恢复结果，再执行代码 3，所以不会从头重跑代码 1。执行完毕后，`resumeWith` 再通过 `completion.resumeWith(outcome)` 交付最终结果；若恢复的是异常，`getOrThrow()` 会抛出，并由此处的 `catch` 向完成续体传递。

`title` 在挂起前产生、挂起后还需要使用，所以示意中存入 `savedTitle`。`result` 则来自 `withContext` 的返回或恢复结果。编译器只需保留后续需要的信息，实际还可能优化掉可重建的值；不需要保存整个线程栈，也不是每挂起一次就重新创建整份状态机。



# 🌟整体介绍

在 Android 中，协程让一次异步任务可以按“发起工作、等待结果、更新 UI”的顺序书写。它仍需要线程执行代码，但等待时可以保存进度并让出线程，不必为每次等待占住一条线程。

协程主要依赖suspend、CoroutineContext以及调度器。

1. 协程体是可挂起的代码（suspend的lambda或者函数）。kotlin编译器会特殊处理suspend函数。比如增加 Continuation 参数、生成状态机，保存执行位置和必要变量，使代码能够挂起后继续执行。（具体见上）
2. CoroutineContext 携带 Job、调度器等元素：Job 管理任务生命周期和父子关系，调度器安排协程的启动与恢复在哪个执行环境中进行。
3. 实际挂起时，当前执行片段返回；异步操作完成后触发续体恢复，代码从保存的位置继续执行。

## 🌟完整解析

1. 创建 MainScope：此时没有启动协程

2. 调用 launch：创建 Job，并提交到主线程

   - 对于这种方式：

   ```
   private val scope = MainScope()
   scope.launch {}
   ```

   1. 先创建 CoroutineScope，传入指定的调度器和任务树的根。
      - 对于 CoroutineScope 的工厂方法，没有Job就会内部自己创建一个。
   2. 调用 `launch` 时，创建关联到根 Job 的子协程对象，并按启动策略启动协程体。
   3. 默认启动会创建续体，由 Context 中的调度器包装续体，再发起首次恢复。
   4. 普通 Main 将恢复任务通过 `Handler.post()` 提交到主线程，主线程取得执行机会后运行协程体。

3. `withContext(IO)` 保存 Main 调用者的续体，在 IO 执行代码块，并等待它返回结果。

4. IO 把可执行任务交给IO调度器，工作线程恢复续体后执行用户代码。

5. 定时器恢复 IO 续体，IO 完成后再恢复外层 Main 续体，Main续体内部可以获取调度器从而恢复到主线程中。

## 调用 launch：创建 Job，并提交到主线程

### 分析

```kotlin
public fun CoroutineScope.launch(
    context: CoroutineContext = EmptyCoroutineContext,
    start: CoroutineStart = CoroutineStart.DEFAULT,
    block: suspend CoroutineScope.() -> Unit
): Job {
    val newContext = newCoroutineContext(context)
    val coroutine = if (start.isLazy)
        LazyStandaloneCoroutine(newContext, block) else
        StandaloneCoroutine(newContext, active = true)
    coroutine.start(start, coroutine, block)
    return coroutine
}
```

本例没有额外传入上下文，因此继承 `scope` 的 Main 调度器和父 Job；创建出的 `StandaloneCoroutine` 是本次任务自己的 Job。`launch()` 返回它，**返回并不表示任务已经完成**。



```
scope.launch
  → AbstractCoroutine.start
  → CoroutineStart.DEFAULT.invoke
  → block.startCoroutineCancellable
```

`commonMain/intrinsics/Cancellable.kt`

```kotlin
internal fun <R, T> (suspend (R) -> T).startCoroutineCancellable(
    receiver: R, completion: Continuation<T>,
) = runSafely(completion) {
    createCoroutineUnintercepted(receiver, completion)
        .intercepted()
        .resumeCancellableWith(Result.success(Unit))
}
```

- **`createCoroutineUnintercepted`**：创建协程体的原始续体（状态机），绑定 `receiver` 和完成回调 `completion`，此时还没执行协程体。

- **`intercepted`**：通过 Context 中的调度器，将原始续体包装成 `DispatchedContinuation`，使其具备调度能力。

- **`resumeCancellableWith`**：发起首次恢复，按调度器安排执行，并检查取消状态，未取消才开始执行协程体。这里的 `Unit` 是启动信号。



## 进入 withContext：主线程交出执行机会

```kotlin
return suspendCoroutineUninterceptedOrReturn sc@ { uCont ->
    val oldContext = uCont.context
```

# 可取消挂起与 delay

1. 内部创建一个可取消续体与当前job关联
2. 以delay为例，通过Main或IO的计时器，然后挂起
3. 基于suspend运转机制：到期且未取消时，按原调度器恢复续体，状态机继续执行；如果等待期间 Job 被取消，则清理定时任务，并使挂起调用以 `CancellationException` 结束。

## delay源码

```kotlin
public suspend fun delay(timeMillis: Long) {
    if (timeMillis <= 0) return // don't delay
    return suspendCancellableCoroutine sc@ { cont: CancellableContinuation<Unit> ->
        // if timeMillis == Long.MAX_VALUE then just wait forever like awaitCancellation, don't schedule.
        if (timeMillis < Long.MAX_VALUE) {
            cont.context.delay.scheduleResumeAfterDelay(timeMillis, cont)
        }
    }
}
```

## 先创建可取消续体，登记定时恢复

`suspendCancellableCoroutine` 的核心步骤如下：

```
val cancellable = CancellableContinuationImpl(
    uCont.intercepted(),
    resumeMode = MODE_CANCELLABLE
)

cancellable.initCancellability() // 关联当前 Job 的取消通知。
block(cancellable)             // 执行上面的定时恢复登记。
cancellable.getResult()        // 尚未完成时返回挂起标记。
```

于是当前协程挂起，当前线程结束这段任务，能够执行其他工作。

## Main 和 IO 分别怎样实现计时

`delay` 根据当前协程的 Context 选择计时设施：

```
internal val CoroutineContext.delay: Delay
    get() = get(ContinuationInterceptor) as? Delay ?: DefaultDelay
```

| 当前调度器   | 谁负责计时                     | 到期后在哪里继续           |
| ------------ | ------------------------------ | -------------------------- |
| Android Main | Main 对应的 Handler            | 主线程                     |
| IO           | 默认配置下的 `DefaultExecutor` | 经 IO 调度器安排到工作线程 |

**Main：利用 `Handler.postDelayed()`。**

**IO：把定时任务放入默认计时器的延迟队列。**

## 取消如何提前结束这次等待

前面的 `initCancellability()` 会读取当前 Job，并登记取消关联：

```
// installParentHandle() 源码节选。
val parent = context[Job] ?: return null
val handle = parent.invokeOnCompletion(handler = ChildContinuation(this))
```

这个 `ChildContinuation` 节点设置了 `onCancelling = true`，因此 Job 开始取消时就会通知它，不必等到整个任务彻底结束。

取消链如下：

```
launch 的 Job 被取消
  → 通知等待中的 CancellableContinuation
  → 将续体置为取消状态
  → 执行取消清理
      Main：移除 Handler 中的延迟回调
      IO：释放、移除尚在队列中的定时任务
  → 安排续体以 CancellationException 恢复
  → delay 抛出取消异常，执行必要的 finally
```

# Dispatcher 与 withContext：安排执行位置

## 常见调度器

调度器（`CoroutineDispatcher`）是 `CoroutineContext` 中的一个元素，负责安排协程代码在哪个线程或线程池上执行。Android 中常见的选择如下：

| 调度器 | 执行位置 | 适用场景 |
| --- | --- | --- |
| `Dispatchers.Main` | 主线程，通过 Handler 入队执行 | 更新 UI、处理轻量 UI 状态 |
| `Dispatchers.Main.immediate` | 主线程；已经在主线程时可直接执行，避免再次入队 | 同样用于 UI，但要注意代码可能立即开始执行 |
| `Dispatchers.Default` | 共享后台线程池，按 CPU 资源限制计算并行度 | 排序、大量数据转换等 CPU 密集任务 |
| `Dispatchers.IO` | 共享后台线程池，允许更多阻塞任务并行 | 同步文件读写、阻塞式网络请求 |
| `Dispatchers.Unconfined` | 开始在调用线程执行，挂起后的恢复线程由挂起操作决定 | 特殊底层场景，普通 Android 业务通常不用 |

`IO` 和 `Default` 共享底层线程池，但任务类型和并行度策略不同，因此在两者之间切换不保证换一条物理线程。`delay` 这样的异步等待不阻塞线程，直接在 Main 调用即可，无需为了等待切到 IO。参见 [Kotlin 调度器介绍](https://kotlinlang.org/docs/coroutine-context-and-dispatchers.html)与 [IO 文档](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-dispatchers/-i-o.html)。

## 调度器怎样安排续体执行

调度器实现了 `ContinuationInterceptor` 接口，以这个 Key 保存在 Context 中。协程启动或恢复时，`intercepted()` 可以从 Context 取得调度器，再调用它的 `interceptContinuation()`，把原始续体包装成 `DispatchedContinuation`。包装结果会被缓存。

[CoroutineDispatcher.kt 源码节选](https://github.com/Kotlin/kotlinx.coroutines/blob/1.10.2/kotlinx-coroutines-core/common/src/CoroutineDispatcher.kt)：

```kotlin
public final override fun <T> interceptContinuation(continuation: Continuation<T>): Continuation<T> =
    DispatchedContinuation(this, continuation)
```

这里的 `this` 是调度器，`continuation` 是原始续体；**`intercepted()` 返回的是包装后的续体，不是调度器。** 包装后的续体在恢复时，先判断是否需要调度，再决定怎样恢复原始续体。

下面用伪代码表示 [DispatchedContinuation](https://github.com/Kotlin/kotlinx.coroutines/blob/1.10.2/kotlinx-coroutines-core/common/src/internal/DispatchedContinuation.kt) 的核心逻辑，省略取消检查、结果保存和防止递归调用过深的事件循环：

```kotlin
fun resumeWith(result) {
    if (dispatcher.isDispatchNeeded(context)) {
        dispatcher.dispatch(context, Runnable {
            continuation.resumeWith(result)
        })
    } else {
        continuation.resumeWith(result)
    }
}
```

恢复原始续体后，编译器生成的状态机继续执行挂起点后面的代码。调度器负责安排线程，状态机负责记住执行位置。

```kotlin
// Toast.makeText(context, title, Toast.LENGTH_SHORT).show()
```

# 普通 Job 与 SupervisorJob 如何传播异常

> **小结**：普通父 Job 会因子任务失败而取消兄弟任务，Supervisor 只隔离直接子任务的失败。

[JobSupport.kt 源码](https://github.com/Kotlin/kotlinx.coroutines/blob/1.10.2/kotlinx-coroutines-core/common/src/JobSupport.kt)：

```kotlin
public open fun childCancelled(cause: Throwable): Boolean {
    if (cause is CancellationException) return true
    return cancelImpl(cause) && handlesException
}
```

[Supervisor.kt 中的关键覆盖](https://github.com/Kotlin/kotlinx.coroutines/blob/1.10.2/kotlinx-coroutines-core/common/src/Supervisor.kt)：

```kotlin
// SupervisorJobImpl 和 SupervisorCoroutine 都使用这条策略。
override fun childCancelled(cause: Throwable): Boolean = false
```

返回 false 表示不因该子任务失败取消自身，也没有替子任务消化异常。监督关系中的 `launch` 仍需处理未捕获异常，否则可能进入 Android 的未捕获异常处理流程并导致崩溃。

Demo 的任务树可进一步理解为：

```text
MainScope 的 SupervisorJob
├─ 第一次点击的 launch A
│  ├─ A 内部 async X
│  └─ A 内部 async Y
└─ 第二次点击的 launch B
```

X 失败会取消普通父协程 A，并影响 Y；根 SupervisorJob 使 A 的失败不继续取消 B。**监督没有自动覆盖所有后代层级。** 根被主动取消时，A、B 仍都会取消。

需要允许某个并发结果失败时，用 `supervisorScope` 并在其内部处理：

```kotlin
suspend fun loadWithOptionalBadge(): String = supervisorScope {
    val title = async { delay(100); "Kotlin" }
    val badge = async<String> {
        delay(50)
        throw java.io.IOException("徽标不可用")
    }
    val badgeText = try {
        badge.await()
    } catch (e: CancellationException) {
        throw e
    } catch (e: java.io.IOException) {
        "暂无徽标"
    }
    "${title.await()} / $badgeText"
}
```

如果异常从 `supervisorScope` 的代码块本身逃逸，它仍会失败并取消剩余子任务。Supervisor 不等于忽略所有错误。

## try/catch 与 CoroutineExceptionHandler 的位置

> **小结**：可恢复的业务失败在协程体内处理，Handler 处理已经未捕获的异常。

下面的异常边界包住实际挂起调用：

```kotlin
// 放在 CoroutineContent 中；repository、file 由调用方提供。
private fun loadText(repository: TextRepository, file: java.io.File) {
    scope.launch {
        try {
            val result = repository.read(file)
            Toast.makeText(context, result, Toast.LENGTH_SHORT).show()
        } catch (e: CancellationException) {
            throw e
        } catch (e: java.io.IOException) {
            Toast.makeText(context, "读取失败，请重试", Toast.LENGTH_SHORT).show()
        }
    }
}
```

把 `try/catch` 放在 `scope.launch { ... }` 外面，通常只包住提交动作，接不到稍后发生的协程体异常。`catch (Exception)` 和 `runCatching` 都可能吞掉 `CancellationException`，需要保留取消语义。

`launch` 对未处理异常的最终处理入口见 [StandaloneCoroutine 源码](https://github.com/Kotlin/kotlinx.coroutines/blob/1.10.2/kotlinx-coroutines-core/common/src/Builders.common.kt)：

```kotlin
override fun handleJobException(exception: Throwable): Boolean {
    handleCoroutineException(context, exception)
    return true
}
```

例如，给 MainScope 的直接子 launch 配置日志 Handler：

```kotlin
val handler = CoroutineExceptionHandler { _, error ->
    Log.e("CoroutineDemo", "任务未捕获异常", error)
}
// scope.launch(handler) { ... }
```

Handler 不能让失败协程从抛错处继续执行，也不能替代业务错误状态。普通子协程会向父任务委托异常处理；`async` 则把异常存入 Deferred，同时仍遵守父子失败规则，所以不能指望给 async 配 Handler 来读取结果错误。

## 超时也是一种取消

> **小结**：超时取消本次操作，不能强制终止不配合取消的工作。

```kotlin
suspend fun loadWithDeadline(): String? = withTimeoutOrNull(500) {
    delay(1_000)
    "完成"
}
```

本例返回 `null`。[Timeout.kt 中触发超时的源码节选](https://github.com/Kotlin/kotlinx.coroutines/blob/1.10.2/kotlinx-coroutines-core/common/src/Timeout.kt)：

```kotlin
// TimeoutCoroutine.run()
override fun run() {
    cancelCoroutine(TimeoutCancellationException(time, context.delay, this))
}
```

`withTimeout` 会抛 `TimeoutCancellationException`；`withTimeoutOrNull` 只把属于自身这次超时的异常转换为 null，外部取消和其他错误仍应传播。代码块本身也可返回 null 时，业务需要额外区分“合法空结果”和“超时”。

超时具有异步性。资源的取得与释放应在同一受保护范围内，例如 `use`、`try/finally`；不能假定资源在块内创建成功，就一定能穿过超时返回边界交付给调用者。
