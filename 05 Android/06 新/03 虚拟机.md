# Dalvik 虚拟机

Dalvik 是 Android 早期使用的应用运行时，执行专为移动设备设计的 DEX（Dalvik Executable）字节码。它面向低内存设备，负责代码执行、线程与堆管理、异常处理和垃圾回收等工作。

Dalvik 最初以解释执行为主，Android 2.2 开始引入 JIT（Just-In-Time，即时编译），在运行时将热点字节码编译为机器码。

## 特点

- 基于寄存器架构，通常能用较少的指令完成计算。
- 使用 DEX 文件集中存放多个类，并合并重复的常量信息，减少文件体积。
- 每个应用通常运行在独立的 Linux 进程中，并拥有自己的运行时实例。
- 提供类加载、线程管理、内存管理、异常处理和垃圾回收等能力。

## 执行流程

![Dalvik 执行流程](/Users/mezzsy/知识点/img/32.png)

构建工具先将 `.class` 文件转换为 `.dex` 文件；应用启动后，类加载器加载所需类，再由解释器或 JIT 编译器执行 DEX 字节码。

# ART 虚拟机

## 什么是 ART

ART（Android Runtime）从 Android 5.0（API 21）起取代 Dalvik，成为 Android 的默认应用运行时。ART 仍然执行 DEX 字节码，因此原有 APK 通常不需要修改即可运行。

Android 5.0 中的 ART 主要在安装时通过 `dex2oat` 进行 AOT（Ahead-Of-Time，预先编译），减少运行时编译开销。Android 7.0 起，ART 引入基于运行画像的 JIT 与 AOT 混合编译，只优先编译热点代码，以平衡启动速度、运行性能、安装时间和存储占用。

## 优点

1. 改善应用启动速度和运行性能。
2. 优化垃圾回收，减少暂停时间和内存碎片。
3. 根据运行画像编译热点代码，兼顾性能与存储空间。
4. 提供更完善的调试、异常诊断和性能分析能力。

## 代价

ART 需要保存编译产物，并在安装后或设备空闲时进行编译，因此可能增加存储占用和编译开销。实际影响取决于 Android 版本、应用规模和编译策略。

# Dalvik 虚拟机和 Java 虚拟机的区别

Dalvik 与传统 JVM 都能运行由 Java 源码产生的程序，但两者执行的字节码、文件格式和指令架构不同，不能直接互换。

| 对比项 | Java 虚拟机（JVM） | Dalvik 虚拟机 |
| --- | --- | --- |
| 执行文件 | `.class` 文件中的 Java 字节码 | `.dex` 文件中的 Dalvik 字节码 |
| 指令架构 | 基于栈 | 基于寄存器 |
| 文件组织 | 通常一个类对应一个 `.class` 文件 | 多个类合并到一个或多个 `.dex` 文件 |
| 设计目标 | 通用 Java 运行环境 | 面向 Android 移动设备 |

Android 构建工具会将 `.class` 文件转换为 DEX。DEX 会合并多个类中的重复信息，减少文件数量和存储占用，也更适合 Android 的加载方式。

# ART 虚拟机与 Dalvik 虚拟机的区别

## 编译方式

Dalvik 主要采用解释执行和 JIT，只在运行时编译热点代码。ART 在 Android 5.0 中侧重 AOT；现代 ART 则结合解释执行、JIT、运行画像和 AOT，在不同阶段优化代码。

## 垃圾回收

Dalvik 的垃圾回收更容易产生较长的应用暂停，频繁回收时可能导致卡顿。ART 改进了并发标记、对象回收和堆压缩等机制，缩短暂停时间并降低内存碎片。

## 内存管理

Dalvik 使用的非移动式回收更容易留下不连续的空闲空间。ART 可通过移动式回收器整理对象，并对大对象采用专门的内存区域，从而提高内存利用率。具体策略会随 Android 版本和设备配置变化。

## Multidex 支持

Android 5.0 及以上的 ART 原生支持从 APK 加载多个 DEX 文件；Android 5.0 以下的 Dalvik 通常需要 AndroidX Multidex 库协助加载次级 DEX。

# Android APK 编译打包流程

![Android APK 编译打包流程](/Users/mezzsy/知识点/img/32.png)

现代 Android 构建通常由 Android Gradle Plugin 统一协调，主要流程如下：

1. Kotlin 或 Java 源码被编译为 `.class` 文件；AAPT2 同时编译、链接资源并生成资源索引。
2. D8 将 `.class` 字节码转换为 DEX；启用代码压缩时，R8 还会完成压缩、优化和混淆。
3. DEX、资源、清单和原生库等内容被打包为 APK。
4. APK 先通过 `zipalign` 对齐，再使用 `apksigner` 签名，得到可安装文件。

整体可概括为：源码与资源编译 → DEX 转换 → 打包 → 对齐 → 签名。

# 64K 问题

单个 DEX 文件的方法引用索引最多容纳 65,536 项，包括应用代码、依赖库和 Android Framework 中被引用的方法。超过限制时，构建会出现 `Too many method references` 等错误。

常见解决方式如下：

1. 删除无用依赖，避免引入体积过大的库。
2. 启用 R8，移除未使用的代码。
3. 启用 Multidex，将代码拆分到多个 DEX 文件。

当 `minSdk` 不低于 21 时，ART 原生支持加载多个 DEX；当 `minSdk` 不高于 20 时，还需要配置 AndroidX Multidex 库。
